# 改善 Tab 主 PRD

> iSho 第二个 Tab 的指导方针级 PRD。按 Apple 设计方法论 7 层收敛漏斗组织。
> 每一层给出**结论**与**取舍逻辑链路**。不列防御性砍项清单。
> 状态：v1.0（2026-04-23）— L1-L2 完稿，L3-L8 骨架待填。

---

## L1 · 问题定位

### 一句话产品定位

> **iSho 的第二个 Tab。"我累了 / 我睡不着"时不给孤立建议、也不给内容库让你自己挑——给你一条可信的改善路径：选定目标 → 解释当前 → 多维度解法 → 此刻可做 / 可听 / 可读的内容节点。把 CBTI 等临床方法论消费电子化。**

### 用户原话与场景

| 场景 | 频率 | 用户原话 | 用户真实问题 |
|---|---|---|---|
| 日间即时不适 | 高频 | "我累爆了怎么办" | 现在就要改善 + 要知道怎么做 |
| 睡前即时不适 | 高频 | "我睡不着怎么办" | 今晚想好睡 + 要一套方法 |

**延展场景**（不作为独立入口，是即时不适消费完后的自然延展）：

- 为什么我会这样 · C 科普阅读
- 今晚 / 今日还能怎样 · B 行动延伸
- 长期改善路径 · D 习惯养成

### iSho 两个 Tab 的心智对子

| 场景 | 用户原话 | 承接 Tab | 答案形态 | 消费深度 |
|---|---|---|---|---|
| 晨起 | "今天能不能打仗" | Homepage | 高能时长数字 + 分档 | 轻（~30s） |
| 日间自觉下滑 | "我是不是真到点了" | Homepage | 当前时段对照 | 轻（~30s） |
| 日间即时不适 | "我累爆了怎么办" | 改善 Tab | 改善路径（目标 - 当前 - 解法） | 中（3-15 min） |
| 睡前即时不适 | "我睡不着" | 改善 Tab | 改善路径（目标 - 当前 - 解法） | 中（3-15 min） |

**Homepage = 诊断 · 轻消费 · 数据可视化；改善 Tab = 行动 · 中消费 · 内容节点。两个 Tab 消费深度分工明确。**

### 取舍逻辑链路

1. **场景聚焦"即时不适"** —— 用户对"睡眠 / 精力改善"的诉求形态多样（即时缓解 / 今日行动 / 长期习惯 / 认知科普），但用户原话最多的始终是"我现在 X"的即时诉求。其余三类是即时诉求阅读完后的自然延展（B/C/D），不作为独立入口。
2. **此 Tab 天然回避与大模型竞争** —— 即时不适场景下，用户不会打一段字描述状态给大模型再等回答。iSho 的 Homepage 已经知道用户当前状态，用户不需要重述。这是 iSho 相对通用对话 AI 的**结构性壁垒**。
3. **"App 代你判断"权力分配 · 跨 Tab 一致** —— Homepage 已确立此权力分配（诊断权在 App）。改善 Tab 继承（行动推荐权在 App）。同一产品的两个 Tab 必须共享权力分配，否则用户会精神分裂。
4. **不和 Calm / Headspace 正面竞争** —— 它们按通用类目陈列内容货架，用户自己找"我现在需要什么"；改善 Tab 基于（当下状态 × 目标 × 画像 × 历史消费 × 偏好）动态组织路径，**给你一个**而不是**给你一排**。

## L2 · 核心对象「改善路径」

### 一句话定义（onboarding 级）

> **「改善路径」—— 从你选定的目标（提神 / 助眠入睡）出发，经过引擎对你当前状态的多维度诊断，给出对应的解法卡，每张卡承载一段 3-15 分钟可做 / 可听 / 可读的内容节点。每条路径根据你、场景、历史消费、偏好动态组织。**

### 心智模型

| 维度 | 采用 | 砍掉 |
|---|---|---|
| 核心对象 | 改善路径（目标 - 当前 - 解法三段论 · 树状） | 单点建议 / 内容分类库 / 视频列表 |
| 组织方式 | 动态生成（目标 × 画像 × 状态 × 历史消费 × 偏好） | 预制决策树 / 话术库 / 固定分类 |
| 主位节点 | 引擎推的"此刻最先做的"（唯一 CTA） | 多 CTA 并列 / 让用户自己挑 |
| 分支展示 | 次位卡可见可点（体现树状） | 只露主位 / 折叠起来 |
| 信任来源 | 逻辑透明（目标 · 诊断 · 解法都摊开）+ 临床背书（方法体系明示） | 评分 / 热度 / 推荐榜 |
| 权力分配 | App 选逻辑，用户走逻辑 | 用户挑内容 |
| 内容价值 | 逻辑骨架上的节点 | 可独立消费的 SKU |
| 消费深度 | 中消费（3-15 min）为主，重消费辅 | 轻消费（Homepage 已覆盖） |

### 三段论 · 医生工作流的消费级化身

改善路径的结构与医生工作流**同构**，这不是巧合，是刻意的：

| 医生工作流 | 改善 Tab 结构 |
|---|---|
| 主诉 | §1 用户选定的目标（提神 / 助眠入睡） |
| 鉴别诊断（多维度） | §2「你当前的情况」多诊断并列 |
| 处方（对应诊断） | §3 解法卡（1:1 对应诊断） |
| 推荐优先项 | 主位卡有 CTA · 其他次位卡无 CTA 突出 |
| 追问 / 随访 | 节点消费完的「没明白」Agent 追问 / 「收藏」偏好记录 |

这是 "CBTI 消费电子化" 的结构体现 —— 不是把 CBTI 简化，是把 CBTI 的推理链条用消费级的 UI 呈现。临床的严谨藏在结构里，用户看到的是干净的三段落。

### 取舍逻辑链路

1. **改善路径 vs 单点建议** —— 健康场景中孤立建议（"去深呼吸"）无法承担信任：用户不知道为什么、凭什么、对不对。目标 - 诊断 - 解法三段论让用户"看懂就信了"。信任靠**逻辑可见**，不靠品牌或权威。
2. **改善路径 vs 内容库** —— 内容库把判断权让给用户（自己挑），与 Homepage 的"App 代你判断"权力分配**矛盾**。同一产品两个 Tab 必须一致，否则用户精神分裂。
3. **树状而非单线** —— 临床逻辑本来就是分支结构（CBTI / 正念 / 生理节律 / 睡眠卫生 各自服务不同机制）。UI 压成单线会抹掉产品的专业感。多维诊断 × 多张解法卡 1:1 映射，树状自然浮现，用户不需要被教育"这是树"。
4. **动态组织 vs 预制话术库** —— 方法体系多元，(目标 × 画像 × 状态 × 历史消费 × 偏好) 的组合无法穷举。系统必须具备"由多维输入组装一条路径"的能力 —— 这是 `path-engine` 模块的存在理由。
5. **消费电子化的真正含义** —— 不是简化 CBTI（那会失效），而是把临床严谨嵌入消费级的语言 + 交互。像 Apple Watch 的 ECG —— FDA 级精度 + 普通人能按的一根表冠。改善 Tab 是 CBTI 的类似化身。
6. **为什么内容代表产品调性** —— 逻辑链只是骨架，每个节点的文字 / 音频 / 练习是产品的"音色"。粗糙节点让再好的逻辑失效。内容生产流程（文献 → AI 提炼 → 人工精选 + 真人录音）是调性源头，写入 L3 气质章节约束。

## L3 · 首屏结构与气质（下一轮展开 · 骨架）

本节将展开下列已讨论成熟的内容：

- **L3.1** 首屏结构 v3（树状）—— §1 目标 / §2 当前诊断 / §3 解法树 / §4 延展
- **L3.2** 首屏交互 —— 目标切换整屏刷新的时序、loading 文案、禁止部分刷新
- **L3.3** 页面性格与气质 —— 对标反例表、Do/Don't 表、视觉基调、声音基调
- **L3.4** 节点消费完成态 —— 知识性内容（明白了 / 没明白 → Agent）+ 音频类内容（收藏 / 再听 / 换一段）
- **L3.5** 首屏动态更新规则 —— 3 源组装（当前场景 / 历史消费 / 偏好库）+ 降权规则
- **L3.6** 「查看更多」入口 —— 解法卡右上角 `更多 ↗` → 主题深度页（二级）
- **L3.7** Agent 登场点 —— 仅在节点消费后的「没明白」/「告诉我感觉」，利用已消费上下文

**首屏 5 条硬约束**（本节将展开每条的 Do/Don't）：

1. **逻辑可见** —— 目标、当前、解法、延展全部首屏可见，不藏折叠
2. **动态组织** —— 目标 × 画像 × 状态 实时生成，禁止话术模板轮播
3. **主位 = 引擎推的"此刻最先做的"** —— 有 CTA；其他分支次位可见可点，但无 CTA 突出
4. **临床源头明示** —— 每张解法卡标方法体系（CBTI / 放松训练 / 睡眠卫生 / 生理节律 …）
5. **诊断 1:1 映射解法** —— §2 几个维度，§3 就几张卡，数量严格对齐

## L8 · 模块切分（待填）

### UI 模块（首屏 + 下钻）

| 中文 · 英文 | 职责 | 位置 |
|---|---|---|
| 首屏 Hero · `hero` | §1 目标 + §2 当前诊断 + §3 解法树 | 首屏·顶至中 |
| 延展位 · `path-extensions` | §4 路径相关（为什么 / 今晚 / 长期） | 首屏·底 |
| 节点消费 · `content-consumption` | 阅读器 / 播放器 + 两套完成态尾屏 | 全屏沉浸 |
| 主题深度页 · `topic-detail` | 「更多 ↗」指向的同主题延伸 | 下钻·二级 |
| Agent 追问 · `agent-followup` | 「没明白」后承接已消费内容上下文的对话 | 下钻·二级 |

### 底层引擎模块（非 UI）

| 模块 | 职责 |
|---|---|
| `path-engine` | 3 源组装：当前场景 × 历史消费 × 偏好库 → §2 §3 §4 实时生成 |
| `profile-engine` | 用户画像持续更新（Onboarding + Status 数据 + 使用行为 + Agent 识别） |

### 外部契约（不在本需求内）

- **sleep-window** —— §1 日 / 夜目标默认值切换依赖 `推荐入睡时间`。锚点待 sleep-window master PRD 完成后补。
- **Homepage / Status Tab** —— §2 当前诊断的数据输入来自 Homepage 的（分档 × 时段 × 事件流）。契约待 Homepage 补充"对外暴露的状态摘要字段"。
- **Onboarding 画像** —— `profile-engine` 静态画像源头。属独立 PRD，待立项。

### 本次不含（走独立 master PRD）

- Onboarding（首次打开画像建立）
- 用户画像长期维护机制
- 内容生产流程规范（文献 → AI 提炼 → 人工精选 + 真人录音 的 SOP）
- 音频真人录音的拾音 / 发音人选择 / 背景噪声规范
