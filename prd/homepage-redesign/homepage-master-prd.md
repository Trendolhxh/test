# Homepage 主 PRD

> iSho Homepage 的指导方针级 PRD。按 Apple 设计方法论 7 层收敛漏斗组织。
> 每一层给出**结论**与**取舍逻辑链路**。不列防御性砍项清单。
> 状态：v1.0（2026-04-21）。

---

## L1 · 问题定位

### 一句话产品定位

> **告诉用户今日头脑清晰时段分布的 App。晨起 30 秒回答"今天能不能打仗"，自觉状态下滑时回答"我的感觉对吗、下一段高能什么时候来"。**

### 用户原话与场景

| 场景 | 频率 | 用户原话 | 用户真实问题 |
|---|---|---|---|
| 晨起 | 最高频 | "我昨晚醒了好多次，今天是不是废了？" | 今天状态好不好 + 最佳时段在哪 |
| 日间自觉下滑 | 中频 | "我是不是真到点了？还能不能再撑一场？" | 对照感觉 + 下一段高能何时来 |

### 取舍逻辑链路

1. **场景全部来自睡眠相关情境**——用户自述 3 个高频场景（晨起难受 / 晨起愉悦 / 睡前助眠），无一涉及"日间精力查询"，原方案的"午后低谷"场景是 PM 强加，不在用户心智里。
2. **定位选"眼睛看今天"而非"眼睛看昨晚"**——后者退化为睡眠报表（Oura/Whoop 路线），前者才是独特价值："把昨晚翻译成今天"。
3. **聚焦两个高频场景，不追求全天覆盖**——参照 Apple Weather / Sleep Cycle："每天那一刻不可替代"优于"每天打开 N 次都还凑合"。场景单一不是缺点，是定位。
4. **场景"晨起愉悦"是场景"晨起难受"的副产品**——前者的答案天然被后者的答案覆盖（在二级页归因里），无需为其单独设计首屏。

## L2 · 核心指标「高能时长」

### 一句话定义（onboarding 级）

> **「高能时长」——你今日头脑清晰、不易疲劳的时间总长。**

### 心智模型

| 维度 | 采用 | 砍掉 |
|---|---|---|
| 数字性质 | 总长度 | 预算 / 剩余 |
| 随时间变化 | 全天稳定 | 递减（像电量） |
| 动态信息 | 由"当前时段 + 下一段"承担 | 由数字掉速承担 |
| 正负情绪 | 正面（你拥有 N 小时） | 负面（你还剩 N 小时） |
| 比喻 | 天气预报（今日将在 10:00-12:00 晴） | 手机电量 |

### "总量" 与 "时段分布" 分离

- **总量** = 今日头脑清晰时间的累计小时分钟数（如 `7h 29min`）
- **时段分布** = 该总量最可能出现在一天的哪些时段（如 10:00-12:00 + 15:30-17:00）

两者由**不同算法路径**产出。总量承担稳定性，分布承担动态性。**不同步调整**。

### 取舍逻辑链路

1. **定义采用感受视角**（头脑清晰 / 不易疲劳），不是能力视角（集中注意力 / 认知输出）：用户可对照当下感受自证，不需懂医学；不限定知识工作者，商业扩展性高；与场景 1"今天是不是废了"形成反义对照。
2. **心智采用稳定总量 + 时段分布**，不是电量预算递减：人不是电池，状态是波动的；"剩余"是负面框架，与"让用户头脑更清晰"的初心矛盾；日间用户关心"下一段何时来"而非"还剩几小时"——这是时序分布问题，不是预算余额问题。
3. **保留「高能时长」命名**：已有流行语感，沉没成本高；代价是 onboarding 必须一句话定义背书，并保证全产品不再出现"精力""能量""恢复度"等近义模糊词。
4. **总量稳定性边界**：允许算法在睡眠质量完全重估（如午睡 30min+）或检测到急性生理异常时重算，但**禁止**因"时间流逝"或"日间任务消耗"自动下调——后者是电量心智的残留。

## L3 · 首屏结构

### 结构全景

```
╭─────────────────────────────────────╮
│                                     │
│          [ 气场渐变背景 ]            │  纯装饰
│                                     │
│              7h 29min               │  Hero 数字（全天稳定）
│           今日头脑清晰时长           │  功能副标题
│                                     │
│        ─────  当前状态条  ─────      │  1 个支持元素（动态）
│                                     │
╰─────────────────────────────────────╯

 交互：
  · 点击 Hero     → 二级页 · 归因分析
  · 点击状态条     → 二级页 · 罗盘时间轴
```

### 3 条硬约束（违反即失败）

1. **结构一致**：晨起 / 上午 / 午后 / 下午 / 傍晚打开，看到的是同一个结构，**只有状态条文案变化**。不做"时段态分裂首屏"。
2. **正面框架**：Hero 数字**不随时间递减**。传递"你拥有多少"而不是"你还剩多少"。
3. **渐进披露**：归因（"为什么今日是这个数字"）放二级页。首屏只回答"是什么（Hero）"和"现在怎样 / 下一段何时（状态条）"，**不回答"为什么"**。

### 状态条文案库

| 时刻 | 算法判断 | 状态条文案 |
|---|---|---|
| 晨起 | 首段尚未开始 | `首段高能 10:00-12:00 即将开始` |
| 首段前（8:00-10:00）| 等待中 | `首段高能 10:00-12:00，再等 X 分钟` |
| 首段中（10:00-12:00）| 高能中 | `正处于今日首段高能时段` |
| 过渡（12:00-15:30）| 低能期 | `当前低能期，下一段 15:30-17:00 开始` |
| 次段中（15:30-17:00）| 高能中 | `正处于今日次段高能时段` |
| 尾段（17:00-）| 已结束 | `今日高能时段已结束，明日见` |
| 单峰模式 | 单段 | `正处于今日高能时段` / `今日高能时段 10:00-13:00` |
| 极低能 | 分散无明确段 | `今日头脑清晰时段较分散，建议降低任务密度` |

### 取舍逻辑链路

1. **1 Hero + 1 支持元素**，不多不少：多元素 → "6 主角 = 0 主角"；零元素 → 用户不知数字含义，无法指引行动。
2. **支持元素选"当前状态条"而非"归因"**：归因回答"为什么是这个数字"指向昨晚，晨起之后信息就 stale；状态条回答"现在怎样 / 下一段何时"，两个场景（晨起 + 日间）都成立，信息永远时效。
3. **归因收进二级页**：首屏诚信与完整性兼得——用户想知道"为什么"，点 Hero 即得完整多因子分析；不挤首屏则不污染核心判断。
4. **状态条给时段不给行动**：算法门槛太高则给不出准确推荐；陈述事实（"当前低能期"）用户可自验证；推荐行动（"建议把会挪到下午"）一次错误信任即崩。
5. **状态条的归纳粒度是"状态归纳句"**：不挑单因子（误导），不平铺多因子（退化成信号灯）。类比 Apple Weather 的"Mostly Cloudy"而非"湿度 72% + 云量 65% + 风速 8m/s"。

## L4 · 核心 Do / Don't

| 项 | Do | Don't |
|---|---|---|
| Hero 数字 | 稳定显示今日总长 | 倒计时 / 进度条递减 / 实时重算 |
| 副标题 | "今日头脑清晰时长"（固定） | 叙事化文案（"昨晚睡得还不错"） |
| 状态条 | "当前 X，下一段 Y-Z" | "你可能感到疲惫" / 代言用户感受 |
| 归因呈现 | 状态归纳句 + 点开看细节 | 单因子陈述 / 多因子进度条平铺 |
| 指标命名 | 「高能时长」（1 词） | "精力 / 能量 / 恢复度 / 状态分" 混用 |
| 医学表述 | 引用可查证的医学术语 | 自造词（如"神经速质储备"） |
| 气场颜色 | 轻微情绪调色（高/低 对应 凉/暖） | 承担信息（红黄绿进度感） |
| 心率等辅助数据 | 二级页 / 按需呈现 | 常驻首屏 |
| Agent 入口 | 延后或置于二级 / 三级 | 作为首屏主角 |

### 名词审计规则

- 保留的词（如「高能时长」）必须有 onboarding 定义背书
- 新术语上线前做 Do/Don't 配对检验：能否写出"正确用法"和"错误用法"两个具体例子？不能则不得使用
- 自造医学 / 神经科学术语 = 产品诚信红线，一律不允许

## L5 · 消失测试结论

消失测试：若同时存在 Hero 数字 + 信号灯仪表盘 + Agent 对话文案，**删任意一边 App 都不塌** —— 两者互为冗余。

**强制选边**：保留**仪表盘派**（Hero 数字 + 状态条），砍**教练派**（首屏 Agent 对话）。

理由：现阶段 Agent 无法稳定给出可验证有用的建议；首屏必须由"确定可信"的信息承担（数字 + 时段），不由"概率性生成内容"承担。Agent 延后处理，详见后续模块。

## L6 · 场景 Trigger 与回答映射

| 场景 | 用户原话 | 用户真实问题 | Hero 数字呈现 | 状态条呈现 |
|---|---|---|---|---|
| **晨起（最高频）** | "我昨晚醒了好多次，今天是不是废了？" | 今天好不好 + 最佳时段何时 | `7h 29min` + 功能副标题 | `首段高能 10:00-12:00 即将开始` |
| **日间自觉下滑（中频）** | "我是不是真到点了？还能不能再撑一场？" | 对照感觉 + 下一段何时来 | `7h 29min`（同一数字，不变） | `当前低能期，下一段 15:30-17:00 开始` |

### 关键一致性

- Hero 数字从早到晚**只有一个值**，不随时间改写。
- 状态条文案**随时间轴切换**，对齐当前所在时段。
- 二级页归因在两个场景中都是一致入口（点 Hero）。

## L7 · 相较原 6 屏截图的显式砍项清单

| 砍掉项 | 原位置 | 砍的理由 |
|---|---|---|
| "昨晚睡得还不错" / "午后精力低谷" 等叙事文案 | 首屏副标题位置 | 与 Hero 数字 + 气场色 100% 冗余；代言用户感受，信任风险高 |

| 首屏 Agent 聊天入口 | 首屏底部 | 消失测试结果：Agent 与 Hero+状态条互为冗余；算法不稳时首屏不放生成内容 |

| "精力 / 能量 / 恢复度 / 状态分" 等近义模糊词 | 原 PRD 散见 | 「高能时长」已承担命名成本；全产品禁止近义替代词 |

## 附录 A · Q&A 推导过程（14 轮精简版）

> 仅保留关键转折。每轮记录：**问题 → 结论 → 取舍逻辑**。完整副本见 `/Users/trendol/.claude/plans/subagent-lexical-crescent-agent-a9a9b35d3c2a1435c.md`。

### Round 1 — 评审触发

- **输入**：6 屏截图 + 4 份 PRD + HTML demo。
- **结论**：apple-design-reviewer 评判 **退回重做，卡在 L1**。
- **关键红线**：首屏 6 主角 = 0 主角、「高能时长」语义二义性、"神经速质储备"伪术语、截图与 v1.2 PRD 不一致。

### Round 2 — 场景清单

- **问**：用户为哪些真实场景打开这个 App？
- **用户答**：3 个场景——晨起难受 / 晨起愉悦 / 睡前难受。均与睡眠相关。原截图"午后低谷"不是用户原话，是 PM 强加。
- **结论**：**删"日间精力查询"作为独立场景**；"午后低谷"退化为"自觉状态下滑时的验证查询"（非主动触发）。

### Round 3 — 场景取舍

- **问**：3 个场景是否全做？
- **结论**：场景 2（晨起愉悦）= 场景 1 的副产品，同一屏解决；场景 3（睡前助眠）是完全不同产品逻辑，不做。
- **取舍**：参考 Apple Weather / Sleep Cycle，"每天那一刻不可替代"优于"全天都凑合"。

### Round 4 — 定位方向

- **问**：App 是"眼睛看昨晚"还是"眼睛看今天"？
- **结论**：**眼睛看今天**。看昨晚退化为睡眠报表（Oura / Whoop 路线），不是本产品。
- **一句话定位 v1**：*"一款把昨晚睡眠翻译成今天可用时长的 App。"*

### Round 5 — 核心指标一句话定义

- **问**：「高能时长」如何向用户 onboarding 解释？
- **候选**：能力视角（集中注意力 / 认知输出） vs 感受视角（头脑清晰 / 不易疲劳） vs 混合。
- **结论**：**感受视角**——"你今日头脑清晰、不易疲劳的时间总长"。
- **取舍**：用户能自证、不限定人群、与场景 1 的"废了"形成反义。

### Round 6 — Hero 数字呈现形式

- **问**：数字用 "小时分钟"（7h 29min）还是百分比（78%）？
- **结论**：小时分钟。百分比需分母，分母不存在就无意义；小时分钟是总长度，心智更稳。

### Round 7 — 电量/预算心智（被后续推翻）

- **当时结论**：晨起"今日可用"，日间"今日剩余"，耗尽"已用完"。
- **状态**：此轮暂定，但在 Round 11 被推翻。

### Round 8 — 1 支持元素选哪个

- **问**：Hero 之下唯一的支持元素放什么？候选：归因 / 状态条 / 行动建议。
- **结论**：**状态条**（即 Round 11 反思后的当前状态 + 下一段）。
- **取舍**：归因指向昨晚，信息会 stale；行动建议算法门槛高，错一次信任即崩；状态条陈述事实，用户可自验证，时效性强。

### Round 9 — 归因呈现形式

- **问**：归因放哪里？怎么呈现？
- **结论**：**二级页** + **状态归纳句**（如"昨晚中断较多，恢复偏低"）。
- **取舍**：不单挑某一因子（误导），不平铺多因子（退化成信号灯）。类比 Apple Weather 的"Mostly Cloudy"。

### Round 10 — 「高能时长」命名去留

- **问**：要不要改名（如"认知密集工作时段"）？
- **结论**：**保留**。沉没成本高、已有语感；代价：onboarding 必须一句话定义背书，全产品禁用近义模糊词。

### Round 11 — L1 级反思：电量心智推翻

- **用户 pushback**：
  1. 人不是电池，状态是波动的。
  2. "剩余"是负面框架，与"让用户头脑更清晰"的初心矛盾。
  3. 日间用户真正关心"下一段何时来"，不是"还剩几小时"——这是时序问题，不是预算问题。
- **结论**：**心智从"电量倒计时"改为"稳定总量 + 时段分布"**。
- **连锁修正**：
  - Hero 数字全天稳定，不随时间递减。
  - 动态信息由状态条承担（当前所在时段 + 下一段起止）。
  - 副标题改为"今日头脑清晰时长"（固定文案，不再有"剩余/可用"变体）。

### Round 12 — 首屏 3 条硬约束定稿

- 结构一致 / 正面框架 / 渐进披露——违反任意一条即判定失败。

### Round 13 — 状态条文案库

- 产出 8 种时段状态的文案范式（晨起 / 首段前 / 首段中 / 过渡 / 次段中 / 尾段 / 单峰 / 极低能）。
- 原则：给时段不给行动、陈述事实不代言感受。

### Round 14 — 总量稳定性边界

- **问**：数字既然不递减，什么情况可以变？
- **结论**：允许——睡眠质量完全重估（午睡 30min+）、急性生理异常；禁止——时间流逝、日间任务消耗自动下调。
