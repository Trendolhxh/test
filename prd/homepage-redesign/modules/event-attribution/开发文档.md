# 事件归因 · `event-attribution` · 开发文档

> 本文档从 PM 视角描述 event-attribution 模块的**功能完整逻辑**——做什么、不做什么、数据从哪里来、有哪些状态、怎么切换、异常时用户看到什么。**不规定**接口签名、数据结构、缓存机制、性能预算等工程实现细节，这些由开发自决。
>
> **UI 已由 Figma 直出**（节点 1449-3279 / 1449-3476 + 后续夜间版）。本文档不重复描述卡片视觉细节，只定义**数据 → 卡片槽位**的映射逻辑与**交互 / 状态 / 异常**的业务规则。

## 1. 功能边界

### 1.1 本模块做什么

| 元素 / 行为 | 说明 |
|---|---|
| **事件归因大卡** | 一次展示一条事件的归因信息：事件 icon + 事件名 + 时长·时段 + impact 数值组（数字 + 单位 + 指标标签）+ 归因大标题（headline）+ 归因小字（narrative）+ 1-3 条快捷问题 chips |
| **多事件切换** | 本次冷启动区间内有多条新事件时，横划切换；每次只展示一张卡 |
| **日 / 夜双版文案** | 同一事件的 `headline` / `narrative` / `prompts` 有日间版 + 夜间版；impact 数值 / 单位 / 标签也随当前 hero mode 切换 |
| **模式联动** | 订阅 hero 的 mode 变化，mode 切换时整组卡片同步切换文案（事件集合不变、卡片位置保持） |
| **整卡隐藏** | 本次冷启动以来无新事件时，整个 event-attribution 区域不渲染（不占位） |

### 1.2 本模块不做（明确归属）

| 不做 | 归谁 |
|---|---|
| 今日全部事件列表 / 历史事件回顾 | `today-tab`（独立 tab） |
| 事件对应的 24h 曲线 / 时段分布 | `energy-detail`（点 hero 主数字进） |
| hero 主数字 / 分档 / 状态行 | `hero` |
| mode 的判定与切换（日 / 夜的权威方） | `hero`（本模块仅订阅） |
| 事件原始数据的产出（HealthKit 映射、`impact` 计算、`headline` / `narrative` / `prompts` 文案生成） | 上游事件流服务 + LLM 文案服务（本模块只消费成品字段） |
| Agent 对话入口 / 会话承载 | v1 整体不做；chips 在 v1 不可点 |
| 卡片就地展开曲线 / 事件详情 / 内嵌对话流 | v1 显式不做 |

### 1.3 与其他模块的协同关系

- **与 `hero` 的 mode 联动**：见 [hero §1.3 / §3.3 不变量 #2 / §4.2](../hero/开发文档.md)——hero 是 mode 权威方、同组齐换、切换动效节奏对齐。**本模块的响应细节**：mode 切换时事件集合不变、卡片横划位置保持、仅换对应 mode 版文案（详见 §3.5 不变量 #3）
- **与 `shared/事件数据.md` 的消费关系**：`event.title` / `impact` / `headline` / `narrative` / `prompts` 全部直接渲染到卡片槽位，不二次加工
- **与 `shared/一日窗口.md` 的消费关系**：用该契约判定"事件是否落在当前一日窗口内"（与冷启动游标取交集，详见 §3.2）
- **与 `today-tab` 的关系**：同一份 Event 流的两种视图——today-tab 是全量历史视图，event-attribution 是冷启动增量视图；**数据源同一、呈现策略不同**

## 2. 数据来源与权威方

每一行说明：**这个元素的内容来自哪里、谁是修改它的权威方**。本模块不在端侧二次计算 / 翻译 / 阈值判定。

| 卡片槽位 | 数据来源 | 权威方 | 本模块端的处理 |
|---|---|---|---|
| **事件 icon** | `event.subtype` → `shared/事件数据.md §2.1` 5 类 icon token 映射（`sleep` / `nap` / `exercise` / `walking` / `common`） | 共享契约 | 按 subtype 查 token，渲染对应 icon；不在端侧造新 icon |
| **事件名**（卡片主文字） | `event.title` | 上游事件流服务 + 共享契约 §2 | 直接展示；超 12 字按 [shared/文案长度.md](../../shared/文案长度.md) 末尾 `…` 截断 |
| **事件时长·时段**（如 `33 min · 07:15 – 07:48`） | `event.duration` + `event.start_at` + `event.end_at` 拼接 | 上游事件流服务 | 端侧按固定格式拼接；不二次格式化时间 |
| **impact 主数字 + 单位 + 指标标签** | `event.impact` 数组中匹配当前 hero mode 主指标的那一条 | 上游事件流服务（`impact` 按 [共享契约 §2](../../shared/事件数据.md)） | 按当前 mode 选条、拆数字 / 单位 / 标签三段；不自行计算影响 |
| **归因大标题** | `event.headline` 的日间版 / 夜间版（按当前 hero mode 选） | 上游事件流服务（**规则生成**） | 直接展示；超 12 字末尾 `…` 截断 |
| **归因小字** | `event.narrative` 的日间版 / 夜间版（按当前 hero mode 选） | LLM 文案生成服务（**大模型生成**） | 直接展示；超 71 字末尾 `…` 截断 |
| **快捷问题 chips** | `event.prompts` 的日间版 / 夜间版（按当前 hero mode 选），最多取前 3 条 | LLM 文案生成服务（**大模型生成**） | 直接渲染；单条超 10 字末尾 `…` 截断；超 3 条不展示多余 |
| **右下角 arrow icon** | 静态 UI 元素（非数据驱动） | 本模块 | 点击 → 跳转 Agent 对话页（携带 `event.id`）；详见 §4.4 |
| **当前 hero mode** | hero 模块广播 | `hero`（详见 hero §3.1） | 订阅 mode 变化事件；不持有 mode 状态 |
| **事件集合筛选** | 冷启动游标 `last_cold_start_at` + 一日窗口起点 + `event.ingested_at` | 本模块 + 一日窗口契约 | 详见 §3.1 |

### 通用约束

- 所有卡片文案都来自 `event.*` 字段或对应共享契约；**本模块不另起文案库**——业务文案修改全部回到上游事件流服务或 LLM 文案生成服务
- 数据未到达时一律走 §5 异常态 / 整卡隐藏，不在端侧造假兜底
- `impact` 字段若不存在匹配当前 mode 的指标条目，按 §5 处理

### 2.1 文案生成分工

卡片上出现的文案按**生成方式**分两类——各自的稳定性约束与降级策略不同：

| 槽位 | 生成方 | 稳定性保证 | 失败时表现 |
|---|---|---|---|
| 事件名 · 事件时长时段 · impact 数字/单位/标签 | 上游事件流服务（**规则 / 算法**） | 同一事件多次读取稳定不变；字段缺失 = 数据异常 | 走 §5 |
| **归因大标题** `headline` | 上游事件流服务（**规则模板**） | 固定句式槽位 + 事件生理指标填槽（如 `{形态描述} · {关键指标名 + 数值}`）；同一事件多次读取**稳定不变** | 若规则生成失败 → 走 §5 降级 |
| **归因小字** `narrative` | LLM 文案生成服务（**大模型生成**） | **不保证**同一事件多次生成文案字字相同；保证语义稳定、不违反主文档 §L4 Do/Don't（不代言感受 / 不因果断言 / 不行动建议）、不超长 | 若 LLM 返回空 / 超时 → 走 §5 降级 |
| **快捷问题 chips** `prompts` | LLM 文案生成服务（**大模型生成**） | 同上；条数 1-3 条不保证次次相同 | 若 LLM 返回空 → chips 区隐藏，卡其他部分正常 |

**业务含义**：
- `headline` 是**规则产物**——开发可以在本地缓存同一事件的 `headline`，跨冷启动 / 跨 mode 切换读取稳定
- `narrative` / `prompts` 是**生成式产物**——同一事件可能在不同冷启动批次里 LLM 产出略有差异，是预期现象
- 端侧**不校验** LLM 文案内容（不做反黄 / 反广告 / 违禁检测——归上游 LLM 服务）；端侧**只按 `shared/文案长度.md` 截断**超长文案

## 3. 状态与转移规则

本模块的**全部内部状态只有 3 个**——游标、事件集合、当前卡片位置。所有别的信息（mode / 事件字段内容 / 当前是什么文案）都是**派生**的，不持有。

### 3.1 冷启动游标 `last_cold_start_at`

#### 定义

- 游标 = **上次冷启动后成功渲染首屏，且用户在前台停留 ≥ 3 秒** 的系统本地时间
- "成功渲染首屏" = event-attribution 模块收到 hero 的 "mode 已就位 + 数据 ready" 信号且完成一次渲染（整卡隐藏也算一次渲染）
- "3 秒" 是**防闪退 / 秒退秒开** 的最小停留阈值——避免用户冷启动瞬间强杀被计入一次有效会话

#### 更新时机

| 场景 | 游标动作 |
|---|---|
| 本次冷启动成功渲染首屏且前台停留 ≥ 3 秒 | **更新**为本次冷启动时刻（不是"成功渲染 3 秒后的时刻"——为避免"这 3 秒里的事件"被下次冷启动遗漏） |
| 本次冷启动 3 秒内闪退 / 被系统杀 / 用户强杀 | **不更新**，下次冷启动仍用上一个游标 |
| Tab 切走 / 后台数小时 / app 长时间闲置回到前台 | **不触发冷启动**，游标不动 |
| 冷启动跨过了"一日窗口"起点（上次睡眠时刻或兜底 05:00） | **强制重置**游标为当前一日窗口起点；确保用户次日打开能看到"新一日的全部事件" |

#### 持久化

- 游标持久化到本地存储；冷启动 / 强杀 / 系统重启都不清除
- 只有"用户清除 App 数据 / 重装 App / 首次安装" 才失去游标——此时初始化为"当前一日窗口起点"（见 [shared/一日窗口.md](../../shared/一日窗口.md) 契约）

### 3.2 事件集合（本次区间快照 · `current_batch`）

#### 定义

- **冷启动成功 → 一次性**从本地事件流筛选 + 排序，形成一个**不可变快照**
- 快照在本次 App 会话内**不变**（哪怕 HealthKit 之后推送了新事件）——即"静态快照语义"，而非"窗口流式语义"
- 下次冷启动时快照被**整个重算**

#### 筛选条件（两层 AND）

1. **层 1 · 新事件判定**：`event.ingested_at > last_cold_start_at`
   - 用 `ingested_at`（事件进入本地存储的时间戳），**不**用 `end_at` / `start_at`
   - 原因：HealthKit 可能延迟推送；事件 `end_at` 是 3 小时前、`ingested_at` 刚才——仍算新事件
2. **层 2 · 一日窗口交集**：`event.end_at ∈ 当前一日窗口`
   - 当前一日窗口 = [上一次 `night_sleep.start_at`, 下一次 `night_sleep.start_at`]，兜底 [05:00, 次日 05:00]
   - 详见 [shared/一日窗口.md](../../shared/一日窗口.md)
   - 避免：前一日的事件今天刚被 HealthKit 拉到，不应混入今日归因

#### 排序规则

**完全复用** [hero §3.2 T2 多事件并存优先级](../hero/开发文档.md) 的规则——按当前 hero mode 主指标的 `impact` 绝对值降序，`影响轻微` = 0 排在最后，绝对值相同时按 `end_at` 大者优先。本模块不重复定义。

#### 快照特性

- 快照生成**只发生在冷启动成功那一刻**；此后本模块**不再感知**新事件推送
- 哪怕用户在 App 开着的情况下完成了一次跑步，该事件**不会**立即出现在大卡——需要下次冷启动
- 这与 hero 状态行 T1 / T2 的"实时感知"形成对比——hero 实时，event-attribution 冷启动快照

### 3.3 当前卡片位置 `cursor_index`

- 值域：`[0, current_batch.length - 1]`
- 冷启动初始化 = `0`（展示 impact 最大的那条）
- 卡片横划左 → `cursor_index + 1`（到末端橡皮筋回弹）
- 卡片横划右 → `cursor_index - 1`（到首端橡皮筋回弹）
- **hero mode 切换时 `cursor_index` 保持不变**——只是卡片内容换成夜间版文案，用户浏览位置不丢

### 3.4 整卡显隐

| 条件 | 行为 |
|---|---|
| `current_batch.length == 0`（本次区间无新事件） | 整卡**不渲染**（不占位、不展示空态文案） |
| `current_batch.length ≥ 1` | 大卡按 `cursor_index` 渲染对应事件的 9 槽位内容 |

> 首页布局联动：本模块整卡隐藏时，下方的 `body-cards` 区域顶部上移；不留空白占位。

### 3.5 全模块不变量

| # | 不变量 |
|---|---|
| 1 | 本模块状态只有 3 个：`last_cold_start_at` · `current_batch` · `cursor_index`——其他都是派生，不持有 |
| 2 | `current_batch` 只在**冷启动**时重算；mode 切换 / 横划切卡 / 下拉刷新都**不**重算 |
| 3 | mode 切换只改变"每张卡渲染的文案版本"，不改变事件集合、不改变卡片位置 |
| 4 | mode 切换触发的文案切换动效的**时长**与 hero 渐隐渐现对齐；**形态**由本模块自决（建议：整卡淡出 → 换文案 → 淡入） |
| 5 | 整卡隐藏（`current_batch == 空`）与"单卡渲染失败"不同——前者无视觉、后者走 §5 异常态 |

## 4. 每个交互的完整逻辑

每个交互列：**何时发生 / 本模块做什么 / 用户最终看到什么**。所有 hero 已定义的机制（手势识别阈值 / 渐隐渐现动效时长 / 自动切换时序等）只引用不重述。

### 4.1 进入首屏（冷启动）

**何时发生**：App 冷启动，用户进入 Status Tab。

**本模块做什么**：

1. 等待 hero 广播"mode 就位"信号（首屏加载时序见 [hero §4.1](../hero/开发文档.md)）
2. 收到信号后一次性生成 `current_batch` 快照：
   - 筛选：`event.ingested_at > last_cold_start_at` AND `event.end_at ∈ 当前一日窗口`
   - 排序：按当前 hero mode 主指标的 `impact` 绝对值降序（§3.2 引 hero §3.2 规则）
3. 初始化 `cursor_index = 0`
4. 根据 `current_batch.length`：
   - `== 0` → 整卡隐藏（§3.4）
   - `≥ 1` → 渲染第 0 张卡的 9 槽位（事件 icon + 事件名 + 时长时段 + impact + headline + narrative + chips + arrow）
5. 本模块自身冷启动动作完成 → 触发"成功渲染首屏" 游标候选；待前台停留 ≥ 3 秒后才落定为新 `last_cold_start_at`（§3.1）

**用户最终看到**：本模块要么完全不显示（区间内无新事件），要么看到一张按 impact 大小排序的第一张大卡。

### 4.2 Tab 切回 / 后台回前台（非冷启动）

**何时发生**：用户从其他 Tab 切回 Status Tab；或 App 从后台回到前台但**未冷启动**。

**本模块做什么**：**什么都不做**——`current_batch` 保持上次冷启动时的快照，`cursor_index` 保持用户上次离开时的位置。

**用户最终看到**：与上次离开 Status Tab 前一模一样的 event-attribution 状态。

> 理由：静态快照语义（§3.5 不变量 #2）——增量事件的"新"只在冷启动时重算；用户通过 Tab 切换 / 后台唤回不会看到卡片突变。

### 4.3 卡片横划切卡

**何时发生**：用户在卡片视觉区域内水平横划。

**手势边界**：

- 手势起始点必须在卡片区域内（起点在 hero 区则归 hero 的 mode 切换，见 [hero §4.2](../hero/开发文档.md)）
- 手势中途跨区域不改判——**按起始点归类**
- 横划阈值由设计按系统 iOS paging scroll 约定（不与 hero 的"过屏宽 1/3"共享；因为语义不同：hero 是切 mode，本模块是翻页）

**本模块做什么**：

| 方向 | 条件 | 动作 |
|---|---|---|
| 左划（翻下一张） | `cursor_index < current_batch.length - 1` | `cursor_index += 1`，渲染新卡 |
| 左划到末卡 | `cursor_index == current_batch.length - 1` | 橡皮筋回弹，不换卡 |
| 右划（翻上一张） | `cursor_index > 0` | `cursor_index -= 1`，渲染新卡 |
| 右划到首卡 | `cursor_index == 0` | 橡皮筋回弹 |
| 单卡批次（`length == 1`） | 任意方向横划 | 橡皮筋回弹（默示"到头"） |

**用户最终看到**：卡片左右切换；末端有"到头"的手感反馈，无 dots / 计数等显式分页指示。

### 4.4 hero mode 切换（被动接收）

**何时发生**：hero 广播 mode 变化（来源可能是：自动切夜 / 自动切日 / 用户横划 hero）。

**本模块做什么**：

1. 收到 mode 变化信号
2. 当前卡片整体淡出（时长对齐 hero 渐隐节奏，见 [hero §4.2](../hero/开发文档.md) 步骤 2-5）
3. 文案切换（事件集合 + 位置**都不动**）：
   - `headline` 换为新 mode 版本
   - `narrative` 换为新 mode 版本
   - `prompts` 换为新 mode 版本
   - `impact` 数字 / 单位 / 标签从 `event.impact` 数组里重新挑匹配新 mode 主指标的那一条
4. 卡片淡入（时长对齐 hero 渐现节奏）

**用户最终看到**：同一事件的大卡"变装"——事件 icon / 事件名 / 时长时段不动；impact 数字和归因文字变成另一套；chips 也变。用户当前浏览到第 N 张卡，切换后仍停在第 N 张。

> 边界：若切换过程中 hero 因"对侧主指标拉取失败"回滚到原 mode（见 [hero §4.2 失败分支](../hero/开发文档.md)）—— 本模块同步回滚到原文案。

### 4.5 点右下角 arrow → 进 Agent 对话页

**何时发生**：用户点击当前展示卡片的右下角 arrow icon。

**本模块做什么**：

1. 触发跳转到 Agent 对话页
2. 携带参数：`event.id`（当前 `cursor_index` 所指事件的 id）
3. Agent 对话页承载什么 / 如何初始化会话 / 如何呈现事件信息卡片与摘要 → **归 Agent 对话模块**（独立 PRD，不在本文档范围）

**用户最终看到**：跳出事件归因大卡所在的首页，进入 Agent 对话页；首屏已经有 Agent 输出的"事件信息卡片 + 摘要文案"。

### 4.6 点 chip → 进 Agent 对话页 + 自动发送该问题

**何时发生**：用户点击当前卡片底部的某条 chip。

**本模块做什么**：

1. 触发跳转到 Agent 对话页
2. 携带参数：`event.id` + `prompt_text`（被点 chip 的完整文案，含截断后 `…`？**不含**——截断只是端侧显示层的 UI 处理，`prompt_text` 传**上游返回的完整原文**）
3. Agent 对话页用 `prompt_text` 作为用户首条消息**自动发出**（由 Agent 对话模块处理）

**用户最终看到**：跳出首页进入 Agent 对话页，Agent 已经在回复刚刚被自动发出的那条问题。

### 4.7 下拉刷新（不响应）

**何时发生**：用户在 Status Tab 首屏下拉触发系统下拉刷新。

**本模块做什么**：**什么都不做**——下拉刷新由 hero 处理（重拉主指标），本模块的 `current_batch` 保持静态快照语义（§3.5 不变量 #2）。

**用户最终看到**：hero 区刷新 skeleton → 新主指标，event-attribution 区保持不变。

> 理由：若下拉刷新也重算 `current_batch`，用户一次无意识的下拉就可能看到卡片突然多 / 突然少，违反"冷启动快照"的稳定承诺。要看到新事件，需要下次冷启动。

## 5. 异常情况 → UI 状态映射

每条异常给出**降级策略** + **用户最终看到**。本节按用户说的"状态问题最后一次性解决"原则先给默认方案 + 7 处 ⚠️ 标记待 PM review，不穷举所有分支。

### 5.1 冷启动游标异常

规则已在 §3.1 定义，此处不重述。

| 子情况 | 降级 | 用户感知 |
|---|---|---|
| 首次安装 / 本地存储被清 | 游标初始化 = 当前一日窗口起点 | 首次看到今日窗口内全部事件（至少昨夜睡眠） |
| 冷启动 3 秒内闪退 / 秒退 | 游标不更新 | 下次冷启动仍看到这批"新"事件，不丢卡 |
| 跨一日窗口边界冷启动 | 游标强制重置 | 次日打开自然展示"新一日的所有事件" |

### 5.2 事件字段缺失 / 降级

⚠️ 本节的每一条降级策略**待 PM 确认**，默认方案基于"信息完整性优先于卡片美观"——宁可少展示某个槽位，也不展示空占位。

| 缺失字段 | 默认降级 | ⚠️ |
|---|---|---|
| `event.title` | 用 `event.display_name` 兜底；再缺失则整卡不渲染（该事件从 `current_batch` 剔除） | — |
| `event.subtype` 不在 5 类 icon token 内 | icon 用 `common` 兜底（见 [shared/事件数据.md §2.1](../../shared/事件数据.md)） | — |
| `event.impact` 数组中缺少当前 mode 主指标的条目 | impact 数值组**整组隐藏**（卡片右上角留空）；归因其他部分正常展示 | ⚠️ 备选：展示"影响评估中"占位？ |
| `event.impact` 匹配条目的值是 `影响轻微` | impact 主数字位显示 `影响轻微` 文字、单位与标签位隐藏 | ⚠️ 备选：整组隐藏？与"零贡献"视觉上一致？ |
| `event.headline.day/.night` 缺失 | 整卡不渲染（从 `current_batch` 剔除）——归因大标题是规则生成，缺失 = 上游算法失败 | ⚠️ 备选：展示通用兜底 headline？ |
| `event.narrative.day/.night` 缺失或空字符串 | narrative 行**整行隐藏**，卡片其他部分正常展示（卡片高度变矮） | ⚠️ 备选：展示"归因生成中…"占位 |
| `event.prompts.day/.night` 为空数组 | chips 区**整块隐藏**，卡片其他部分正常展示 | ⚠️ 备选：展示固定兜底 chip"了解更多"（v1 Agent 已做，可真跳转） |
| `event.ingested_at` 字段缺失 | 保守视为"非新事件"，从 `current_batch` 排除 | ⚠️ 备选：用 `end_at` 兜底判定 |
| 截断文案在字符边界上截出残字（罕见 utf-8 边界情况） | 按 [shared/文案长度.md §2.2](../../shared/文案长度.md) 的字符边界优先规则处理 | — |

### 5.3 一日窗口契约异常

| 子情况 | 降级 | 用户感知 |
|---|---|---|
| `shared/一日窗口.md` 契约未交付 | 端侧用固定规则兜底：[本地 05:00, 次日 05:00] | 用户无感；与兜底规则一致 |
| 契约存在但睡眠数据未就绪 | 按契约兜底到 05:00 规则（与 §3.2 一致） | 用户无感 |

### 5.4 上游事件流 / LLM 文案服务异常

| 子情况 | 降级 | 用户感知 |
|---|---|---|
| 本地事件流存储读取失败 | `current_batch = 空`，整卡隐藏 | 同"无新事件"无差异 |
| LLM 文案生成服务批量失败（多条事件都缺 narrative） | 走 §5.2 单条 narrative 缺失降级——narrative 行隐藏 | 卡片还在、只是少一段归因文字 |
| LLM 返回内容违反主文档 §L4 Do/Don't（代言感受 / 因果断言等） | 端侧**不校验**；归上游 LLM 服务的 guardrails | — |

### 5.5 Agent 对话页跳转失败

| 子情况 | 降级 |
|---|---|
| 点 arrow / chip 后跳转 Agent 对话页失败（路由错 / 模块未就绪） | 归 Agent 对话模块处理，本模块**不做**兜底 UI；本模块只负责发出跳转意图 |

### 5.6 并发边界

| 子情况 | 降级 |
|---|---|
| hero mode 切换动效进行中，用户卡片横划 | 当前 mode 切换动效完成后，立即响应用户横划；不打断 mode 切换 |
| 用户卡片横划动效进行中，hero 触发 mode 切换 | 等卡片横划动效完成，再响应 mode 切换 |
| 用户快速连续横划（1 秒内连切 N 次） | 按最后一次停留位置渲染，中间过程不触发埋点 |

## 6. 埋点

只采集**用户感知到的状态变化**与**回答产品问题需要的维度**。

### 6.1 用户感知事件清单

| 事件 | 何时触发 | 想回答的产品问题 | 应抓的维度 |
|---|---|---|---|
| event-attribution 首次可见 | 冷启动后卡片完成渲染（`current_batch ≥ 1` 的情况） | 多少比例的用户进 App 能看到新事件卡？mode / 事件类型 / batch size 分布如何？ | 当前 mode / 焦点事件 `subtype` / `current_batch.length` / 首屏耗时 |
| 整卡隐藏 | 冷启动后 `current_batch == 0`  | 多少比例的用户遇到"无新事件"？按时段 / 用户画像分布如何？ | 当前 mode / 一日窗口起点 / 上次冷启动时间差 |
| 卡片横划切卡完成 | 用户横划后卡片位置变化并稳定 | 用户翻多少张卡？首卡 / 末卡的 drop-off？ | 前 `cursor_index` / 后 `cursor_index` / `current_batch.length` / 本次 session 累计横划次数 |
| 点 arrow 进 Agent 对话 | 用户点当前卡片的 arrow icon | 哪类事件的用户更倾向进 Agent？转化率多少？ | 焦点事件 `subtype` / 焦点事件 `impact` 值 / 当前 mode / `cursor_index` |
| 点 chip 进 Agent 对话 | 用户点当前卡片的某条 chip | 哪类 chip 文案触达率高？chip 1/2/3 位置转化率差别？ | 被点 chip 的 index / 焦点事件 `subtype` / 当前 mode |
| mode 切换触发文案切换完成 | 收到 hero mode 变化广播 + 完成文案切换动效 | hero / event-attribution 的联动是否真的同组齐换？ | `triggered_by_hero_mode_switch = true`（与 [hero §6.4](../hero/开发文档.md) 约定同步）/ 前 mode / 后 mode / 切换耗时 |

### 6.2 数据完整性事件（监控用，非用户感知）

| 事件 | 触发 | 用途 |
|---|---|---|
| 事件字段缺失触发降级 | §5.2 任一条降级路径被命中 | 监控上游服务 / LLM 文案服务的稳定性；提示哪些字段最常缺失 |
| 冷启动 batch 为空但本地事件流非空 | `current_batch == 0` 却存在满足"新事件"判定的事件（说明筛选逻辑漏了） | 监控端侧筛选逻辑的正确性 |
| `impact` 匹配条目缺失 | `event.impact` 数组中缺少当前 mode 主指标的条目 | 监控上游计算服务的覆盖度；提示哪类事件未对夜间 / 日间指标建模 |

### 6.3 不采集的事件

- 分钟级心跳 / 卡片渲染帧率
- mode 切换期间用户的每一次横划尝试
- `current_batch` 快照内的每条事件展示——只在用户"翻到"某卡时算一次查看
- chip / arrow 的按下态 / hover 态

### 6.4 与其他模块的埋点协同

- hero 触发的 mode 切换在**双方**都埋点：hero 侧发"mode 切换完成"，本模块侧发"文案切换完成 + `triggered_by_hero_mode_switch = true`"——形成串联漏斗
- Agent 对话页承载的"事件摘要首屏"不由本模块埋点，归 Agent 对话模块；本模块只埋"跳转意图发出"
