# 核心指标区 · `hero` · 开发文档

> 本文档从 PM 视角描述 hero 模块的**功能完整逻辑**——做什么、不做什么、数据从哪里来、有哪些状态、怎么切换、异常时用户看到什么。**不规定**接口签名、数据结构、缓存机制、性能预算等工程实现细节，这些由开发自决。

## 1. 功能边界

### 1.1 本模块做什么

| 元素 / 行为 | 说明 |
|---|---|
| **主数字** | 二选一：日间 = 今日高能时长（`Xh Ymin`）/ 夜间 = 入睡准备度（`N%`） |
| **副标题** | 与主数字配对的固定文案：`今日头脑清晰时长` / `入睡准备度` |
| **分档** | 4 档评价文字（日：低 / 一般 / 良好 / 卓越；夜：身体仍活跃 / 正在放松 / 已进入放松 / 身体急需休息） |
| **状态行** | 在分档下方一行短文案，按 4 时序优先级展示（T1 进行时 / T2 完成时 / T3 曲线式 / E 异常） |
| **日 / 夜模式切换** | 自动按推荐入睡时间判定 + 用户横划手动覆盖 |
| **下钻** | 日间主数字点击 → 进入二级页 `energy-detail`；夜间主数字 v1 不可点 |

### 1.2 本模块不做（明确归属）

| 不做 | 归谁 |
|---|---|
| 24h 曲线 / 时段分布 / 总量构成 | `energy-detail`（点 hero 主数字进） |
| 事件归因详情大卡 / 事件 narrative / Agent prompts chips | `event-attribution`（独立模块；订阅 hero mode 联动切换） |
| 5 张身体数据卡（心率 / HRV / 活动消耗 / 血氧 / 睡眠） | `body-cards` |
| 高能时长 / 入睡准备度的算法实现 | 计算服务（外部契约） |
| 推荐入睡时间的预测 | `prd/sleep-window/`（独立 master PRD） |
| 事件流原始数据的录入 / 修改 | HealthKit + 后端事件流服务（hero 只读消费） |
| Agent 对话入口 / 会话承载 | v1 整体不做 |

### 1.3 与其他模块的协同关系

- **`hero` 是 mode 的权威方**：日 / 夜模式由 hero 持有；`event-attribution` 订阅 hero 的 mode 变化，事件卡片整组跟随切换（日间事件视图 ↔ 夜间事件视图）
- **`hero` 与 `energy-detail` 顶部数字同源同值**：energy-detail 顶部锚的 `{energy_total}` 来自同一份"高能时长计算"结果，与 hero 主数字必须永远相等；若发现差异以 hero 为准
- **`hero` 是节律时段契约的 v1 唯一消费方**：状态行 T3 曲线式文案需要"当前节律段 + 下一段预测点"（来自共享契约 [shared/节律时段.md](../../shared/节律时段.md)）；其他模块 v1 都不消费此契约

## 2. 数据来源与权威方

每一行说明：**这个元素的内容来自哪里、谁是修改它的权威方**。开发不在 hero 端二次计算 / 翻译 / 阈值判定。

| 元素 | 数据来源 | 权威方 | hero 端的处理 |
|---|---|---|---|
| 日间主数字 `Xh Ymin` | 「高能时长计算」服务的当日累计值 | 计算服务 | 直接展示，不重算 |
| 夜间主数字 `N%` | 「入睡准备度计算」服务的当日值 | 计算服务 | 直接展示，不重算 |
| 4 档分档结果 | 上述两个计算服务返回的 bucket 字段 | 计算服务 | 端侧不存阈值边界，避免端 / 服务双写漂移 |
| 状态行 T1 / T2 的事件名（如 `HIIT 中` / `刚完成跑步`） | HealthKit 最近事件 → 共享契约 [shared/事件数据.md](../../shared/事件数据.md) 的 `display_name` 字段 | 共享契约维护 HealthKit 中文映射 | hero 直接读 `display_name`，不二次翻译 |
| 状态行 T3 的当前节律段 + 下一段预测时间 | 「高能时长计算」/「入睡准备度计算」服务返回的预测段 + 共享契约 [shared/节律时段.md](../../shared/节律时段.md) 的 5 档定义 | 计算服务 + 节律契约 | 按 (当前段, 斜率符号) 二元组查 hero UI PRD §6.3 文案表 |
| 推荐入睡时间（用于自动切夜判定） | sleep-window 模块的「推荐入睡时间」外部契约 | sleep-window | hero 仅消费判定阈值；**不在 UI 上展示该时间** |
| 此刻 `{HH:MM}` | 端侧本地时间 | 端侧 | 状态行 / 副标题等需要 `{HH:MM}` 占位时取本地时间 |

**通用约束**：

- 主数字、分档、状态行的具体文案库锁在 hero UI PRD [§6 文案表](./界面设计.md)。**任何**业务文案修改都改 UI PRD §6，不在开发文档里另起文案表
- 数据未到达时一律走 §5 异常态，不在端侧造假兜底数字

## 3. 状态与转移规则

### 3.1 日 / 夜模式

#### 状态

- **日间**（默认）/ **夜间**
- 每个状态附带"来源"维度：**自动判定** / **手动覆盖**

#### 自动判定规则

| 触发条件 | 切换到 |
|---|---|
| 当前时刻 ≥ 推荐入睡时间 − 3 小时 | 夜间 |
| 检测到夜间睡眠事件 `state = just_completed`（即用户刚起床） | 日间 |

#### 手动覆盖规则

- **触发方式**：用户在 Hero 区域横向滑动（手势详见 §4.2）
- **生效范围**：仅本次 App 生命周期；冷启动后回到自动判定结果，不持久化用户的选择
- **与自动的关系**：手动覆盖发生后，**自动 trigger 仍然存在**——若手动切到日间后，到了推荐入睡时间 − 3 小时，仍然会自动切回夜间。手动覆盖不屏蔽自动判定。

> ✅ **已决（2026-04-23 PM 确认）**：手动覆盖不屏蔽自动判定，**不设冷却窗口**。用户夜间手动切日间后到点被自动切回夜间是**预期行为**——产品立场："临睡时段必须在夜间 mode"高于"用户单次查看日间数据的便利"。

#### 不变量

- 任意时刻只存在一个 mode
- 模式切换时所有联动元素**一次性整体替换**：主数字 / 副标题 / 分档 / 状态行 / event-attribution 事件卡片同步切换；**不允许**"主数字已切夜，副标题还显示日"
- 切换动效统一为 Hero 区域**渐隐渐现**（见 §4.2）

### 3.2 状态行（T1 / T2 / T3 / E）

状态行任意时刻只展示**一条**文案。4 子态优先级**命中即停**：

```
T1（进行时） > T2（完成时） > E（异常） > T3（曲线式）
```

#### 各子态的触发条件

| 子态 | 何时命中 | 文案模板（详见 UI PRD §6.3） |
|---|---|---|
| **T1 进行时** | 存在 `state = in_progress` 的事件（夜间睡眠 / 午睡 / 运动） | `夜间睡眠中` / `午睡中` / `{display_name}中` |
| **T2 完成时** | 存在 `state = just_completed` 的事件，且 `now − end_at ≤ 3 小时` | 按距结束时长 4 档（见下表） |
| **E 异常** | 数据空 / 同步中 / 计算中 / 同步失败任一条命中 | `Apple Health 数据未更新` / `同步 Apple Health 数据…` / `高能时长计算中…` / `数据同步失败 · 点击重试` |
| **T3 曲线式** | 以上都不满足，按当前 metric 形态查表 | 日 5 条 / 夜 4 条（按入睡准备度分档） |

#### T2 的内部时间分段

T2 子态按"距事件结束的时长"分 4 档：

| 距结束 | 文案档位 | 行为 |
|---|---|---|
| ≤ 2 分钟 | "刚刚"档（如 `刚刚起床`） | 进入 T2 默认档 |
| 3 – 59 分钟 | "分钟"档（如 `{N}分钟前醒来`） | 每分钟刷新 N |
| 1 – 3 小时 | "小时"档（如 `{N}小时前醒来`） | 每分钟刷新整点 |
| > 3 小时 | 自动退场 | 状态行重新查表，多半落到 T3 |

#### T3 形态查表

T3 文案按当前 metric 形态决定走哪一条：

- **日间** 5 条对应曲线 5 形态：高能区·持平 / 高能区·上升 / 非高能·下降 / 非高能·上升 / 一日末尾
- **夜间** 4 条对应入睡准备度 4 档：< 50% / 50–79% / 80–99% / = 100%

文案库见 UI PRD §6.3。形态判定依赖共享契约 [shared/节律时段.md](../../shared/节律时段.md)；契约 v1 未就绪时走 §5 降级。

#### 状态行的"切换抗抖"特殊规则

> ✅ **规则（2026-04-23 PM 确认）**：以下是状态行的"切换抗抖"规则——

- 数据更新（首屏加载完成 / HealthKit 推送 / 计算服务返回新值）后，**计数器归零**
- 用户做**第一次**横划切换：状态行按对侧 mode 重新查表，文案随之更新
- 用户连续做**第二次及以后**横划切换：状态行**保持第一次切换后展示的那条文案不变**，即使 mode 在切来切去
- 直到下一次"数据更新"到达，计数器重置；用户下次横划又能让状态行刷新一次
- **目的**：避免用户来回横划体验数字 / 卡片切换时，状态行也成对联动疯狂闪文案，造成视觉抖动

> 等价说法：**状态行的刷新由"数据更新事件"驱动，而不是由"模式切换事件"驱动**。一次数据更新只赋予一次"切换重算配额"。

### 3.3 全模块不变量

| # | 不变量 | 含义 |
|---|---|---|
| 1 | 一次只有一处动 | 主数字位还在 skeleton 时，状态行暂停刷新；状态行切换的瞬间，主数字不重渲 |
| 2 | 模式切换"同组齐换" | mode 变化触发 hero + event-attribution 整组联动一次性切换，不允许任何元素晚一拍 |
| 3 | 横划动效进行中排队自动 trigger | Hero 渐隐渐现期间收到的自动切换信号排队，动效结束再决定是否触发 |
| 4 | 手动覆盖不持久化 | 冷启动 / 强杀重置为自动判定结果；用户上一次手动选择不留 |

## 4. 每个交互的完整逻辑

逐条对应 [UI PRD §4 / §5](./界面设计.md) 的常规与其他状态。每个交互列：**何时发生 → 用户做了什么 / 系统发生了什么 → 走什么分支 → 用户最终看到什么**。

### 4.1 进入首屏（冷启动 / Tab 切回）

**何时发生**：用户从图标 / 推送进入 App，进入 Status Tab；或从其他 Tab 切回 Status Tab 且数据已过期需要刷新。

**逻辑**：

1. Hero 区先进入"加载态"——主数字位用 skeleton、分档不显示、状态行展示 `同步 Apple Health 数据…`
2. 同时取以下数据：
   - HealthKit 授权状态（决定走"空数据"还是正常态）
   - 推荐入睡时间（决定首屏落到日间还是夜间）
   - 当前 mode 对应的主指标（高能时长 或 入睡准备度）
   - 最近一条睡眠 / 运动事件（决定状态行是否走 T1 / T2）
3. 数据齐了：
   - 主数字 + 副标题 + 分档一次性同时呈现（不要主数字先出、分档后出）
   - 状态行按 §3.2 优先级查表命中
4. event-attribution 模块同时收到 hero 的 mode 已就位的信号，开始渲染对应模式的事件卡片

**用户最终看到**：完整的 Hero 区 + 状态行命中 T1 / T2 / T3 之一；event-attribution 卡片同步呈现。

**失败分支**：见 §5。

### 4.2 横划手动切换日 / 夜（最关键交互）

**何时发生**：用户在 Hero 区域水平方向滑动手指。

**手势触发条件**：

- 仅在 Hero 视觉区域内识别（事件卡片区不识别横划——避免与卡片本身的滚动冲突）
- 任意方向（左划 / 右划）都触发同一个动作 = 切到对侧 mode；hero 没有"日 → 夜只能左划、夜 → 日只能右划"的方向区分
- 滑动距离阈值：**过屏宽 1/3 即切**（在"灵敏度"与"防误触"之间折中；具体像素由设计按设备宽度计算）

**逻辑**：

1. 横划手势识别成功
2. Hero 区域整体进入**渐隐**动效（主数字 / 副标题 / 分档 / 状态行同步淡出）
3. 与此同时，event-attribution 收到 mode 即将切换的信号，事件卡片也开始切换动效（具体动效形态归 event-attribution 模块决定，但时长应与 hero 渐隐渐现节奏对齐）
4. 切换中间态：如果对侧 mode 主指标已经缓存好，**直接渲染**（瞬切到位）；若没缓存，整体保持灰色占位 + 状态行展示 `同步 Apple Health 数据…`，等数据返回
5. 对侧数据 ready：Hero 区域**渐现**新内容（主数字 / 副标题 / 分档同时呈现）
6. 状态行按 §3.2 的"切换抗抖"规则决定是否更新（首次切换更新 / 后续保持）
7. event-attribution 完成事件卡片切换

**用户最终看到**：Hero 区从一种 mode 平滑过渡到另一种；事件卡片同步切换；状态行第一次切时跟着变、后续不再变。

**失败分支**：

| 失败场景 | 用户看到 |
|---|---|
| 对侧主指标请求失败 | 主数字位灰色占位 + 状态行 `数据同步失败 · 点击重试`；用户可点击重试 / 也可再次横划切回原 mode（原 mode 缓存仍有效） |
| 横划手势在动效进行中再次发生 | 取消正在进行的渐隐渐现，立即响应新的方向；mode 变化按最新方向走 |

### 4.3 自动切换日 → 夜

**何时发生**：当前时刻达到「推荐入睡时间 − 3 小时」。

**逻辑**：

1. 系统在前台运行时，每分钟检查一次"是否到了切夜的时间点"
2. 命中后，先**预拉夜间主指标**（"入睡准备度计算"服务）；预拉期间 mode 仍然是日间，用户毫无感知
3. 夜间数据 ready 后，触发与 §4.2 相同的渐隐渐现切换（mode 整体替换 + event-attribution 联动）
4. 切换完成后 mode 来源标记为"自动"

**用户最终看到**：Hero 区一次平滑过渡，无加载态闪烁。

**失败分支**：

| 失败场景 | 处理 |
|---|---|
| 夜间主指标预拉失败 | 暂不切换，mode 保持日间；下次轮询（1 分钟后）再尝试 |
| 连续多次预拉失败 | **mode 保持日间**，不强制切换；用户对自动切换失败完全无感，下一个自动 trigger 周期再尝试。**理由**：自动切换是后台无感优化，不应把异常态推到用户面前；用户当晚自己打开 App 时由首屏正常的"加载 → 失败"路径承担失败感知 |

### 4.4 自动切换夜 → 日

**何时发生**：检测到夜间睡眠事件刚刚结束（HealthKit 推送 `state = just_completed`）。

**逻辑**：

1. 收到事件推送，立即取消正在运行的夜间数据轮询
2. 触发日间主指标请求 + 渐隐渐现切换
3. 切换完成后 mode 来源标记为"自动"
4. 状态行按 §3.2 优先级，多半立即命中 T2 完成时档（`刚刚起床`）

**用户最终看到**：用户起床后第一次打开 App，Hero 已是日间形态 + 状态行 `刚刚起床`。

**失败分支**：

| 失败场景 | 处理 |
|---|---|
| HealthKit 推送丢失 / 延迟 | 兜底由前台分钟轮询触发：每分钟主动查 HealthKit 是否有新的 `just_completed` 睡眠事件 |
| 日间主指标计算未完成 | mode 已切到日间，但主数字位 skeleton + 状态行 `高能时长计算中…`；分档不显示；待计算完成后再补齐 |

### 4.5 状态行重试（异常态恢复）

**何时发生**：状态行处于 `数据同步失败 · 点击重试`，用户点击它。

**逻辑**：

1. 状态行立即切到 `同步 Apple Health 数据…`，主数字位回 skeleton
2. 重新触发当前 mode 的主指标请求
3. 单次重试，不做指数退避——让用户自决是否再点
4. 成功 → 状态行按 §3.2 重新查表命中正常子态
5. 失败 → 状态行回 `数据同步失败 · 点击重试`

**用户最终看到**：要么数据回来，要么文案回到失败态等下一次点击。

### 4.6 下钻进 energy-detail（仅日间）

**何时发生**：mode 是日间 + 主数字数据 ready + 用户点击主数字所在区域。

**逻辑**：

1. 触发跳转到二级页 energy-detail
2. energy-detail 自行加载，hero 不为它预加载数据
3. 顶部锚的总值与 hero 主数字必须相等（同源同值约束，详见 §1.3）

**夜间不响应**：mode 是夜间时，主数字所在区域**不响应任何点击**——也不展示可点击的视觉提示（chevron / 按下态 / 涟漪）。这是 v1 显式不做、避免给用户错误的"夜间也能下钻"心智。

## 5. 异常情况 → UI 状态映射

每条异常**必须**对应到 [UI PRD §5](./界面设计.md) 的某一个状态。下面列出 hero 模块需要处理的所有异常源，对应到 UI PRD 哪个状态、用户最终看到什么。

### 5.1 HealthKit 授权异常

| 子情况 | 对应 UI 状态 | 用户感知 |
|---|---|---|
| 首次进入 App，授权弹窗未出现过 | UI §5「空数据」 | iOS 系统授权弹窗 → 用户授予后 hero 自动重试加载；用户拒绝后 → 主数字位灰色占位 + 状态行 `Apple Health 数据未更新` |
| 授权曾给过、用户后期在 iOS 设置里撤销 | UI §5「空数据」 | 同上失败态；hero **不主动**再弹授权窗（避免循环弹窗，授权引导属 onboarding 范畴） |
| 部分类型授权（仅 sleep 给、workout 拒） | UI §5「空数据」 | 视为整体未授权——hero 不做"半授权"半成品状态 |

### 5.2 主指标计算服务异常

适用于「高能时长计算」（日间）/「入睡准备度计算」（夜间）两个服务。

| 子情况 | 对应 UI 状态 | 用户感知 |
|---|---|---|
| 用户当日无数据（服务返回"找不到") | UI §5「空数据」 | 主数字位灰色占位 + 状态行 `Apple Health 数据未更新` |
| 计算异步进行中（服务返回"还在算") | UI §5「计算中」 | 主数字位 skeleton + 状态行 `高能时长计算中…` / `入睡准备度计算中…`；hero 后台继续等待，得到结果后无感更新 |
| 服务故障 / 网络超时 | UI §5「同步失败」 | 主数字位灰色占位 + 状态行 `数据同步失败 · 点击重试` |
| 服务返回的数据缺关键字段（缺分档 bucket 等） | UI §5「同步失败」 | 同上；后台上报数据不完整事件给监控 |

### 5.3 推荐入睡时间契约异常

| 子情况 | 处理 | 用户感知 |
|---|---|---|
| sleep-window 模块 v1 未交付（契约不存在） | 全量走兜底：`推荐入睡时间 = 22:30`；mode 切换阈值固定 = 19:30 | 用户无感（当晚可能 19:30 看到 hero 还在日间 → 19:30 切夜，与正常一致） |
| 契约存在但请求失败 | 同上兜底 | 同上 |

**关键约束**：推荐入睡时间**永不**阻塞首屏渲染——它的失败由"日 / 夜模式判定时间不准"承担用户体验代价，但 hero 不显示任何错误文案给用户。

### 5.4 节律时段契约异常（影响 T3 文案）

| 子情况 | 处理 | 用户感知 |
|---|---|---|
| [shared/节律时段.md](../../shared/节律时段.md) 契约 v1 未交付 | 状态行 T3 整行隐藏（主数字 + 副标题 + 分档仍展示） | Hero 区少一行，但主数字仍清晰可读 |
| 契约存在但当前节律段缺失 / 下一段预测点缺失 | 同上隐藏；不展示半截无意义文案（如 `高能期中` 没有时间） | 同上 |

**理由**：T3 文案的核心信息是 `{HH:MM}` 预测点；预测点缺失则文案无意义。整行隐藏比展示半截更诚实。

### 5.5 状态行 T1 / T2 数据缺失

| 子情况 | 处理 | 用户感知 |
|---|---|---|
| HealthKit 返回事件 `display_name` 字段为空（如新增了未映射的运动类型） | 取通用兜底（如 `运动`）；后台上报 [shared/事件数据.md](../../shared/事件数据.md) 映射缺失事件 | 状态行能显示，但文案泛化（`HIIT 中` 退化为 `运动中`） |
| 事件 `state` 不在 `in_progress` / `just_completed` 枚举内 | 跳过该条事件，状态行降级到 T3 | 用户看到 T3 文案，无 T1 / T2 的事件提示 |
| 事件流整体不可用（HealthKit + 后端都查不到） | 状态行降级到 T3（不显示 T1 / T2） | 同上 |

### 5.6 模式切换的边界

| 子情况 | 处理 | 用户感知 |
|---|---|---|
| 用户在自动切换动效进行中横划手动切换 | 取消自动动效，立即响应手动 | 一次切换动效完成；mode 来源标记为手动 |
| 用户在 just_completed 推送到达瞬间手动切换 | 推送被忽略，按手动处理；推送的 mode 来源标记不生效 | 用户按自己意图看到对侧 mode |
| 设备时间被用户调快 / 调慢 | 自动切换按系统时间走，不做反作弊 | 用户调时间会让自动判定时间漂移，是预期行为 |

## 6. 埋点

只采集**用户感知到的状态变化**与**回答产品问题需要的维度**——不要采集内部 tick / 缓存命中等心跳类事件。

### 6.1 用户感知事件清单

| 事件 | 何时触发 | 想回答的产品问题 | 应抓的维度 |
|---|---|---|---|
| Hero 首次可见 | 首屏数据 ready，Hero 区完整呈现 | 用户进 App 第一眼是日 / 夜？分档分布如何？多少人看到 T1 / T2 / T3 / E？首屏耗时多久？ | mode / mode 来源 / 分档 / 状态行子态 / 首屏耗时 |
| 主数字下钻 | 用户点日间主数字进 energy-detail | 哪些分档 / 哪些状态行的用户更倾向下钻？转化率多少？ | mode（必为日间）/ 分档 / 状态行子态 |
| 模式切换完成 | 任意一次模式切换（自动 + 手动）落定 | 用户横划手动切换的频率如何？凌晨自动切夜的时间分布？手动切换后多久离开？ | from / to / 来源（自动 bedtime / 自动 sleep_completed / 手动横划）/ 整次切换耗时 |
| 状态行子态变化 | 状态行命中态由 X → Y（同档不重报） | T2 时段用户回访率？T3 各形态分布？E 异常出现频率？ | 前一子态 / 现一子态 / 当前 mode |
| 异常态重试点击 | 用户点 `数据同步失败 · 点击重试` | 失败重试成功率？连续失败用户占比？ | mode / 重试前的失败原因 |
| 重试再失败 | 重试后再次失败 | 哪个外部契约最不稳？ | mode / 失败原因 / 当次重试是第几次 |

### 6.2 数据完整性事件（监控用，非用户感知）

| 事件 | 触发 | 用途 |
|---|---|---|
| 外部契约返回不合规 | 计算服务 / 推荐入睡时间契约返回字段缺失 / 格式错 | 监控后端契约稳定性 |
| 主数字短时间剧烈抖动 | 主数字在很短时间内反复变化（具体阈值开发自决） | 监控计算服务收敛性 |
| 事件 display_name 缺失 | HealthKit 事件查不到中文映射 | 监控 [shared/事件数据.md](../../shared/事件数据.md) 映射覆盖度，提示扩表 |

### 6.3 不采集的事件

- 60 秒分钟轮询 tick（即使没切换状态也不报"心跳"）
- 缓存命中 / 未命中的细粒度
- 渲染层动画帧率
- Hero 区不滚动；首页其他区滚动归其他模块

### 6.4 与其他模块的埋点协同

模式切换事件由 hero 触发；event-attribution 在自身的"事件卡片切换完成"埋点中带上 `triggered_by_hero_mode_switch = true`，形成"hero 切换 → event-attribution 联动"的串联漏斗。
