# 上游事件流服务 · 开发文档

> 本文档定义事件流服务的**产品需求**——做什么、何时触发、输出什么、异常时走哪条降级路径。
>
> - 事件实体字段规则以 [shared/事件数据.md](../../shared/事件数据.md) 为准
> - **MVP impact 计算逻辑**（高能时长 + 入睡准备度两个维度 · 研发可直接实现） → [事件影响算法-MVP.md](./事件影响算法-MVP.md)
> - HealthKit 具体类型到 subtype 的映射细则 → 算法侧维护

---

## 1. 功能边界

### 1.1 做什么

- 把 HealthKit 记录的睡眠 / 运动事件转成 [shared/事件数据.md](../../shared/事件数据.md) 定义的 Event 实体
- 维护事件状态（进行中 / 刚完成）
- 产出 headline（规则生成，稳定可复用）和 impact（引用算法结果）
- 在适当时机触发 LLM 生成 narrative / prompts，写回事件记录
- 事件实体持久化到本地存储

### 1.2 不做

| 不做 | 归谁 |
|---|---|
| 高能时长 / 节律时段计算 | 高能时长计算服务 |
| 入睡准备度计算 | `../sleep-readiness/` |
| LLM 文案内容审核 | LLM 服务侧 guardrails |
| 事件列表的筛选 / 排序 / 展示 | `event-attribution` / `today-tab` |
| Agent 对话上下文组装 | Agent 对话模块 |

### 1.3 消费方

| 消费方 | 用哪些字段 | 用的时机 |
|---|---|---|
| `hero` T1 / T2 状态行 | `state` / `display_name` / `end_at` / `impact` | HealthKit 同步完成后即可用 |
| `event-attribution` 归因大卡 | 全部字段 | 冷启动时读取快照 |
| `today-tab` 全量列表 | 全部字段 | 用户进入 Today Tab 时读取 |

## 2. 两阶段管道

本服务的核心产品决策：**规则字段与 LLM 文案分两阶段产出**——前者即时可用，后者异步生成，不阻塞首屏。

### 阶段一 · 同步：HealthKit → Event 实体

**触发**：HealthKit 推送（首选）；前台轮询与后台静默刷新作为兜底。

**产出**：Event 实体除 `narrative` / `prompts` 外的全部字段（见 [shared/事件数据.md §2](../../shared/事件数据.md)），包括 `state`、`impact`、`headline.day/.night`、`ingested_at`。

**时序承诺**：阶段一完成后，事件立即可被 hero T1/T2 和 event-attribution 消费；即使 LLM 尚未生成文案，hero 状态行与 event-attribution 卡片都能正常渲染（narrative 行 / chips 区按降级隐藏）。

### 阶段二 · 异步：App 冷启动 → LLM 批量生成

**触发**：App 冷启动、首屏渲染完成、检测到当日一日窗口内存在 `narrative` 为空的事件。

**v1 先观察策略**：LLM 触发放在冷启动后（而不是 HealthKit 同步完成时），先看实际延时与文案质量再决定是否前移。

**产出**：填充 `narrative.day/.night`、`prompts.day[]/.night[]` 写回本地存储。

**关键约束**：
- 一次冷启动只触发一次 LLM 请求，当日缺文案的事件合并在同一请求
- LLM 请求**不阻塞**首屏渲染
- 写回完成后**不刷新当前 session** 的 event-attribution 卡片——与 event-attribution 的"静态快照"语义一致，下次冷启动才生效

## 3. State 管理

事件状态用于 hero T1 / T2 状态行判定，以及 event-attribution 对"刚完成事件"的识别。

| state | 何时 | 谁更新 |
|---|---|---|
| `in_progress` | HealthKit 事件正在记录中 | 本服务根据 HealthKit 状态写入 |
| `just_completed` | HealthKit 事件已结束 | 本服务在事件结束时更新 |

**3 小时过期规则**：`just_completed` 是否在 hero T2 展示由 hero 端侧基于 `now - end_at ≤ 3h` 自行判定。本服务不持有过期计时器，也不会把 state 改回其他值。

## 4. 规则字段生成原则

### 4.1 impact

描述事件对两个指标（高能时长 / 入睡准备度）的影响，格式见 [shared/事件数据.md §2 impact 字段格式](../../shared/事件数据.md)。

**生成原则**：
- **`night_sleep`**：impact 的高能时长值 = 高能时长计算服务当日结果（绝对值）；本服务在拿到算法结果后写入
- **其他事件**（nap / walking / moderate / vigorous）：impact 值为相对 delta，按 MVP 算法查表产出

MVP 计算逻辑详见 [事件影响算法-MVP.md](./事件影响算法-MVP.md)；升级到"全天重算"完整模型在该文档 §6。

**与高能时长计算的时序关系**：`night_sleep` 的 impact 依赖外部算法结果；若算法尚未返回，impact 字段暂留空，hero T2 仅展示事件名、event-attribution impact 数值组整组隐藏。算法结果到达后补写，下次冷启动生效。

### 4.2 headline

`headline.day` / `headline.night` 由**规则模板**生成——固定句式填入关键生理指标槽位。

**承诺**：
- 同一事件多次读取结果稳定不变
- 每版 ≤ 12 字（超长按末尾 `…` 截断）
- 模板结构、可填槽位 → 字段规则对齐文档

### 4.3 narrative / prompts

由 LLM 在阶段二生成。**承诺**：
- 不代言感受 / 不做因果断言 / 不给行动建议 / 不造伪医学词（对齐主文档 §L4）
- 同一事件多次生成结果可能略有差异（预期现象）
- 端侧不做内容校验，只按 [shared/文案长度.md](../../shared/文案长度.md) 截断

## 5. 异常 → 降级

| 异常 | 处理 |
|---|---|
| HealthKit 推送丢失 / 延迟到达 | 前台轮询 + 后台刷新兜底；延迟事件按延迟时刻的 `ingested_at` 正常入库 |
| HealthKit 未授权 | 事件流为空；hero T1/T2 退化为"空数据"、event-attribution 整卡隐藏 |
| subtype 无法映射 | 算法侧按兜底规则归类；后台上报 mapping 缺失事件 |
| `night_sleep` 的 impact 依赖的算法结果缺失 | impact 字段留空；hero T2 展示事件名、event-attribution impact 数值组隐藏 |
| LLM 超时 / 返回空 / 格式错误 | `narrative` / `prompts` 保持为空；event-attribution 按降级隐藏对应行；下次冷启动重试（每次冷启动只尝试一次） |
| LLM 连续多次失败 | 不做指数退避 / 不永久停止；每次冷启动继续尝试（简单、可预期） |

## 6. 未决项

### 待 MVP 上线后验证

- [ ] **impact MVP 分档阈值**：[事件影响算法-MVP.md](./事件影响算法-MVP.md) 里的 nap / moderate / vigorous 分档值是否符合真实用户体感
- [ ] **vigorous 入睡准备度固定 delta**（-3% / -6%）：若用户反馈与实际感受偏差大，升级到基于 sleep-readiness 真实计算的 delta
- [ ] **LLM 触发时机**（v1 放冷启动后）的实际延时与文案质量；若体验不达预期，考虑前移到 HealthKit 同步完成时
- [ ] **narrative 写回不刷新当前 session** 的体验影响；若用户反馈"看不到文案"，考虑改为实时写回 + event-attribution 监听存储变化

### 待算法侧

- [ ] **headline 规则模板的槽位结构**（各 subtype 的可填槽位与格式）
- [ ] **LLM 输入上下文的摘要字段** → 与 Agent 对话模块确认是否共用同一套 context 组装（避免两套摘要逻辑）
