# 共享契约 · 一日窗口（DayWindow）

## 1. 定义

**一日窗口**是 iSho 全产品的"一天"边界定义。**不按系统日历**的 `00:00 ↔ 24:00` 切分，而是按**用户睡眠周期**切分——使"昨夜睡眠作为当日首条事件"的产品心智成立。

- 语义：一日 = "用户这次睡眠 → 下次睡眠" 之间的清醒 + 活动 + 再次入睡的完整周期
- 粒度：一日是**左闭右开**区间 `[start, end)`——`end` 时刻属于下一日
- 性质：覆盖一天的每一秒，不留空档

## 2. 起止规则

| 边界 | 规则 | 兜底 |
|---|---|---|
| **起点 `day_start_at`** | 上一次已完成（`state = just_completed`）的 `night_sleep.start_at` | 若无可用 `night_sleep` 数据 → 当天本地时间 **05:00** |
| **终点 `day_end_at`** | 下一次 `night_sleep.start_at`（不含） | 若尚未入睡 → 开放端（= "此刻"，即 `day_end_at = null` / 运行时按 `now` 处理） |

### 2.1 为什么选"入睡那一刻"而不是"睡眠结束那一刻"

- 用户心智里，**入睡** = 一日的终结（"今天就这样过去了"）；**起床** = 一日的开始
- 以 `night_sleep.start_at` 为起点意味着：该次睡眠**整体**属于新的一日（"昨夜睡眠"是新一日的首条事件）
- 替代方案"用 `night_sleep.end_at`（起床）作为起点"会把睡眠切成两半（一半归旧日 / 一半归新日），违反"睡眠是事件流的首条"的约束

### 2.2 为什么兜底是 05:00

- 用户常见起床时间段 [06:00, 09:00]；05:00 早于大多数用户的起床时间 → 即使用户当天起床较早，05:00 之前的数据（罕见）被归到前一日也符合直觉
- 避开凌晨 00:00 / 04:00 等"看起来是分界"但用户还在睡觉的时刻——兜底是"替代用户入睡时间"，必须是用户很可能已经醒着的时间

## 4. 边界情况

| # | 情况 | 处理 |
|---|---|---|
| 1 | 用户当日**无** `night_sleep` 发生（未戴表 / HealthKit 未授权 / 失眠彻夜未睡）| 兜底 05:00 生效 → 次日 05:00 作为终点 |
| 2 | 用户连续多日未入睡（极端熬夜） | 一日窗口可能跨越 24h+；按实际 `night_sleep.start_at` 为准，不强切 |
| 3 | 用户一日内有多次 `night_sleep`（跨时区 / 极端作息） | 只取**最晚的那次**作为"本一日的结束"；中间的短睡视为 `nap` |
| 4 | 跨时区飞行 | 按**当前设备本地时区**判定；时区切换瞬间可能出现一次性异常（短日 / 长日），视为预期 |
| 5 | HealthKit 延迟推送：今天才拉到昨晚的 `night_sleep.start_at` | 一日边界按**最新数据**重算；**但不回溯**已展示的 UI（详见 §5） |
| 6 | 睡眠事件的 `state = in_progress`（用户仍在睡） | 一日 `day_end_at` 取该 `start_at`；正在进行的睡眠事件**已属于**新一日（与 `just_completed` 同等归属） |
| 7 | 兜底 05:00 与真实 `night_sleep.start_at` 冲突（极端：入睡时间 03:00，比兜底早）| 真实数据**优先**于兜底；一日起点 = 03:00 不受兜底影响 |

## 5. UI 不回溯原则

若 HealthKit 延迟推送导致一日窗口边界发生后向修正（例：今天 11:00 才拉到"昨晚 23:40 入睡"），**已展示的 UI 快照不重新回算**：

- `event-attribution` 的 `current_batch` 快照保持不变直到下次冷启动
- `hero` 当前展示的状态行 / 分档 / 主数字保持，下次数据更新事件到达时自然刷新
- `energy-detail` 已打开的页面保持当次渲染结果

**理由**：产品不能因"后台拉到的历史数据"让用户正在看的内容突变；一致性优先于"绝对最新"。窗口修正结果只影响**下次**相关模块的读取。

## 6. 与其他契约 / 模块的关系

- **与 `shared/节律时段.md` 的关系**：节律时段的 `phase = night` 段**起点不强等于**本契约的 `day_end_at`——节律 `night` 可能是 22:00 起（按昼夜节律算法），但真实入睡可能是 23:30，本契约用 23:30
- **与 hero 自动切夜（`now ≥ 推荐入睡时间 - 3h`）的关系**：两者是**两个独立维度**——
  - 一日窗口终点用**真实入睡时刻**（事后可知）
  - hero 夜间 mode 用**推荐入睡时间预测**（事前触发）
  - 两者都正确、不互相决定
- **与 `shared/事件数据.md` 的关系**：事件 `start_at` / `end_at` 字段与本契约的 `day_start_at` / `day_end_at` 之间的交集判定由各消费模块自行处理；本契约**不扩事件字段**

## 7. Do / Don't

| # | Do | Don't | 为什么 |
|---|---|---|---|
| 1 | 用 `night_sleep.start_at`（入睡那一刻）作为一日边界 | 用 `end_at`（起床那一刻）/ 系统 00:00 / 本地晚上 23:59 | 入睡 = 一日终结的用户心智；其他切法会让"昨夜睡眠"卡位错乱 |
| 2 | 兜底 05:00 | 兜底 00:00 / 04:00 / 其他 | 05:00 早于大多数用户起床时间，避开"用户仍在睡"的时段 |
| 3 | 左闭右开区间 `[start, end)` | 左闭右闭 / 双开 | 避免 `start_at` 本身归属二义（`start_at` 归新一日、老一日的终点是 `start_at - 1ms`） |
| 4 | 窗口修正不回溯已展示 UI | 因 HealthKit 回填让用户已打开的页面突变 | 一致性优先；回溯让用户不信任"我刚刚看到的就是真" |
| 5 | 一日窗口**不向用户展示** | UI 上写 "您昨晚未戴表，按 05:00 计日" | 底层契约，用户无感；展示会引发"我要不要戴表"的焦虑和困惑 |
| 6 | 端侧按消费模块自决如何用一日窗口 | 在本契约规定具体的 UI 表现 | 契约只管"怎么判定一日"，不管"怎么展示"；UI 决策归各模块 |

## 8. 未决

- [ ] **`sleep-window` 预测契约对接** —— v1 未交付；本契约 §2 `day_end_at` 在"预测下一次入睡"维度暂不参与，沿用"下次真实 `night_sleep` 到达前 = `now`" 的开放端语义
- [ ] **多相睡眠（polyphasic sleep）** —— v1 明确只算 `night_sleep`（最长的那次）为一日边界；多相作息的用户会被误归并，v2 研究
- [ ] **长时段无网 / 无数据同步** —— 设备离线超 24h 时本地 `night_sleep` 可能全部过期；一日窗口依赖 HealthKit 同步就绪，完全离线时走兜底 05:00
- [ ] **时区切换的"跨日异常"持续多久** —— 理论上一次切换只影响一次窗口判定（长/短一日），下一次入睡后自动校准；v2 若发现实际体验差可扩规则
