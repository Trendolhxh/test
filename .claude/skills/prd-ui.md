# prd-ui

为一个模块写**面向设计师**的 UI PRD。读者是设计师，关注的是：这个模块是什么、用户什么时候用、调性如何、默认长什么样、异常时长什么样、具体说什么话。

**写什么 / 不写什么的边界**：UI PRD 是"需求侧"文档——告诉设计师"必须包含哪些元素、必须承担哪些状态、必须用哪些文案"；不是"设计决策"文档——不规定色值、尺寸、字号级差、动效时长、视觉分层权重。前者是 PM 职责，后者是设计师职责。混了就偏。

## 何时触发

- prd-workflow 判定当前处于阶段 3 且用户要写 UI PRD
- modules/<name>/界面设计.md 已有骨架（由 prd-decompose 创建）

## 输入

模块目录路径，例如 `prd/homepage-redesign/modules/hero/`。

## 输出

该目录下的 `界面设计.md`，按 7 节模板填实。

## 核心行为铁律

1. **写前必读**：
   - `../../主文档.md`（重点 §L1 用户场景 / §L3 首屏结构 / §L4 Do-Don't）
   - `../../shared/*.md`（骨架锚点引用的所有契约）
   - 本模块已写的 `开发文档.md` / `产品笔记.md`（避免重复）
2. **分批铁律**：单次 Write/Edit 最多写 1 个 H2。写完停下来问"这一节 OK 吗？进下一节？"
3. **长度目标 100-200 行**。超过 200 行是红色警告——说明又写回设计细节了（典型：给每个元素加 Do/Don't 子节 / 画视觉分层 L0/L1 表 / 写 t0/t1/t2 动效帧 / 内嵌自检清单）。
4. **禁止写**（任一条出现即中断重写）：
   - **具体设计细节**：色值 / 尺寸 / 字号级差 / 动效时长 / 描边粗细 / 饱和度或不透明度数值 / 圆角半径
   - **视觉分层 L0 / L1 / L2 分级表**（层级判断是设计师的工作）
   - **每个元素独立的 Do/Don't 子节 + "为什么"列**（跨全页的 ≤10 条硬约束 Do/Don't 汇总表可以，但作为声明不作为论证）
   - **设计自检清单**（消失测试 / 冗余测试 / 留白测试不写在 UI PRD 里——那是 apple-design-reviewer agent 的职责，不是交付物）
   - **t0/t1/t2 动效关键帧**（交互用"动作 → 结果"二列表达；动效细节交设计）
   - **数据结构 / 字段定义 / 接口契约**（→ 放 开发文档.md）
   - **算法 / 状态机实现**（→ 放 开发文档.md）
   - **PM 的决策依据与取舍理由**（→ 放 产品笔记.md）
5. **文案要能直接用**：UI 里的文字（标题、按钮、空态、错误提示）必须是成品文案，不是占位符。写 `<友好的提示语>` 是失败的。
6. **用户视角优先**：§1 和 §2 必须从用户动作 / 用户问题起笔，不是产品结构描述。反例："Hero 日间主数字的下钻页"。正例："看完首屏总数后，用户在这里看到 24 小时精力的起伏"。

## 章节骨架（固定 · 7 节）

界面设计.md 按以下 H2 组织：

```
# <模块名> · UI PRD

> 锚点块（已由 prd-decompose 生成）

## 1. 一句话
## 2. 用户什么时候用它
## 3. 页面基本性格
## 4. 常规状态
### 4.1 核心元素
### 4.2 核心交互
## 5. 其他状态
## 6. 具体文案
## 7. 未决项
```

## 每节写作指引

### §1 一句话

用户视角的一句话——这个模块在用户手里是什么、解决什么问题。

- 1-2 句，≤ 60 字
- 从用户动作 / 用户问题起笔
- **不**写模块职责分配 / 承担不承担（那是 §2 和 §3 的事）
- **不**写产品结构术语（"下钻页"、"二级页"、"承载区"——这些是给 PM 的，不是用户语言）

### §2 用户什么时候用它

延续 master PRD §L1 的用户场景表。列出用户什么情景下用到本模块、带着什么问题来、从本模块带走什么答案。

格式推荐：

```
| 场景 | 用户带着的问题 | 从本页带走的答案 |
|---|---|---|
| <场景1> | "<用户原话 / 心智问题>" | <本页给的事实> |
```

最后加一句"**本模块不回答 X**——X 归 Y 模块"来划边界（代替冗长的"承担/不承担"对比表）。

### §3 页面基本性格

用 **4-6 条双向度量维度**定位本模块的调性。每条维度是一个 `A ←→ B` 的光谱，标注本模块的位置 + 一句话解释。

对齐 Apple HIG 的 Clarity / Deference / Depth 原则——页面性格必须继承 master §L3 / §L4 的硬约束，不在此节新造偏离。

常用维度参考（按模块实际选 4-6 条，**不全选**）：

- 冷静 ↔ 活泼
- 克制 ↔ 丰富（信息量 / 装饰量）
- 陈述 ↔ 叙事
- 静态 ↔ 动态
- 纯查看 ↔ 可操作
- 专注 ↔ 探索
- 精确 ↔ 模糊
- 当前 ↔ 历史 / 过去 ↔ 未来

格式推荐（每条一个 H3）：

```
### 3.1 冷静 ←━━━━━●━━━━━━━━━→ 活泼 · 强偏冷静

<一句话解释：这个位置具体表现为什么（画面 / 语言 / 动效层面的体现）>
```

**硬约束**：

- 至少 4 条、至多 6 条——少于 4 条 = 没说清调性；多于 6 条 = 在凑数
- 每条位置必须是 `偏左 / 偏右 / 强偏左 / 强偏右 / 居中` 之一，禁止 `适中 / 略偏 / 其实看情况` 这类逃避表达
- 每条解释 ≤ 3 行，只讲 what，不讲 why（why 归 产品笔记.md）
- 若本模块在某条维度上偏离 master 约束，**停下报告 prd-workflow**，而不是写进性格

### §4 常规状态

描述"默认 / 多数用户看到的那一个状态"。分两个 H3：

#### §4.1 核心元素

列出默认态下出现的元素及其"是什么、在哪里"。禁止规定视觉细节（字号、颜色、权重等级）。

```
| 元素 | 内容 | 位置 |
|---|---|---|
| <元素名> | <内容描述（含成品示例文案）> | <相对位置描述> |
```

**硬约束**：常规状态不超过 6 个元素。超过 6 个说明模块要拆、或把某些元素降级到"其他状态"里。

#### §4.2 核心交互

列出核心交互动作 + 结果。只描述"用户做什么 → 会发生什么"，不写 t0/t1 动效帧。

```
| 动作 | 结果 |
|---|---|
| <用户动作> | <页面反应> |
```

结尾可加一行"**不做**：<具体被禁的交互>"来边界化（例如"不做弹窗 / 不做跳独立页"）。

### §5 其他状态

除常规状态外的所有状态穷举成一张表——空、加载、错误、历史日、授权未开、局部失败等。**不为每个状态单独写子节**。

```
| 状态 | 触发 | 视觉要点 | 顶部锚 / 关键文案 |
|---|---|---|---|
| <状态名> | <什么条件进入> | <一句话视觉区别（不规定色值 / 尺寸）> | <文案引用 §6> |
```

**完备性自查**（作者自查，不写在文档里）：

- 空数据
- 加载中
- 错误态
- 历史 / 旧数据（若模块有时间维度）
- 授权未开（若模块依赖 HealthKit 等系统权限）
- 局部失败（若模块有两个以上数据源）

不适用的状态显式标注 `本模块不适用 · <一句话理由>`，不允许省略。

表下可加一行"**状态切换不变量**：<一句话>"来声明跨状态的硬约束（例如"切日期时子态清空"）。

### §6 具体文案

文案库——所有在本 UI 出现的固定文本。按来源 / 用途分子节：

```
#### 6.1 <用途分类 1，例：顶部锚>
| 主态 / 情景 | 文案 | 示例 |
|---|---|---|

#### 6.2 <用途分类 2，例：按钮 / 入口>
...

#### 6.3 <用途分类 3，例：异常 / 空态文案>
...

#### 6.4 变量规范
| 变量 | 来源 | 格式 |
|---|---|---|
| `{var}` | <数据源 / 上游契约> | <显示格式 + 异常态占位> |
```

**硬约束**：

- 文案必须是成品，不允许 `<待定>` / `<友好提示>` / `<TODO>`
- 变量命名与 master PRD / shared 契约一致；本 PRD 不发明新变量（要新发明必须在本节列出来源 + 通知 prd-review）
- 文案不代言感受、不做因果断言、不给行动建议（除非 master 明确允许）—— 违反 master L4 时 prd-review 会阻塞

### §7 未决项

分 2-3 组：**待决策**（需 PM / 设计 / 工程决定后才能继续）+ **v1 延后**（已决定后续版本做的，供回归时直接检视）。

```
#### 7.1 待 PM / 设计决策

- [ ] **<未决项标题>** — 候选: ①…/②…/③… — 卡在: <什么信息未到位>

#### 7.2 v1 延后（已决定后续版本做）

| 功能 | 版本 | 备注（含回归触发条件若有） |
|---|---|---|
```

**硬约束**：每条待决必须给"候选" + "卡在什么"；不允许写"待定"而不说待在哪。v1 延后项若有回归触发条件，必须写出来——否则后续版本启动时没人知道何时该回来做。

## 完成判据

- [ ] 7 节全部填满（或显式标注 `本模块不适用 · <理由>`）
- [ ] 总行数 100-200
- [ ] §1 / §2 从用户视角起笔，不是产品结构描述
- [ ] §3 有 4-6 条双向度量维度，每条位置明确
- [ ] §4.1 元素 ≤ 6 个
- [ ] §5 含完备性自查覆盖的所有状态（不适用显式标注）
- [ ] §6 无占位符
- [ ] §7 未决项每条有候选 + 卡点；延后项有回归触发条件（若适用）
- [ ] 无数据字段 / 接口定义 / 算法细节（属于 dev）
- [ ] 无色值 / 字号 / 动效 ms / 视觉分层 L 级表 / 自检清单（属于设计）
- [ ] 无决策依据 / 取舍理由（属于 pm）
- [ ] 文件头锚点正确指向 master 和 shared

全部满足后：

1. 把文件头的 TODO 注释删除（保留"决策记录"注释块——那是未来版本回归时的检视锚）
2. 提醒用户可以调用 `prd-review` skill 审查
3. 交还给 prd-workflow agent
4. **agent 更新 `prd/<feature>/进度.md`**：该模块"界面设计"格子 ⏸→🟡；review 通过后 → ✅ + 追加变更日志一行
