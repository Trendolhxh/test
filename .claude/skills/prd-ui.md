# prd-ui

为一个模块写**面向设计师**的 PRD。读者是设计师，关注点是：这个模块长什么样、有几种状态、说什么话、怎么动。

## 何时触发

- prd-workflow 判定当前处于阶段 3 且用户要写 UI PRD
- modules/<name>/界面设计.md 已有骨架（由 prd-decompose 创建）

## 输入

模块目录路径，例如 `prd/homepage-redesign/modules/hero/`。

## 输出

该目录下的 `界面设计.md`，按章节填实。

## 核心行为铁律

1. **写前必读**：
   - `../../主文档.md`（读整份，重点 L1-L5）
   - `../../shared/*.md`（骨架锚点引用的所有契约）
   - 本模块已写的 `开发文档.md` / `产品笔记.md`（如果有，避免重复叙述）
2. **分批铁律**：单次 Write/Edit 最多 1 个 H2 或 2 个 H3。写完停下来问"这一节 OK 吗？进下一节？"
3. **长度目标 150-300 行**。超过 300 行是红色警告——说明在写不该写的东西（典型：跑到开发细节去了）。
4. **禁止写**：
   - 数据结构 / 字段定义 / 接口契约（→ 放 dev-prd）
   - 算法 / 状态机实现 / 性能指标（→ 放 dev-prd）
   - PM 的决策依据和未决项（→ 放 pm-notes）
   - Master 已经说清楚的东西（直接引用锚点，别重写）
5. **抽象词 = Do/Don't**：任何形容词（"轻量"、"聚焦"、"自然"）都必须配一对 Do/Don't 具体示例。写不出示例的词直接删掉。
6. **文案要能直接用**：UI 里的文字内容（标题、按钮、空态、错误提示）必须是成品文案，不是占位符。写"<友好的提示语>"是失败的。

## 章节骨架（固定）

界面设计.md 按以下 H2 组织，每节可选择性写入（若本模块不涉及可以整节省略）：

```
# <模块名> · UI PRD

> 锚点块（已由 prd-decompose 生成）

## 1. 定位（一句话 + 在主界面的位置）
## 2. 状态清单（所有可能状态的穷举）
## 3. 内容清单（文案 / 图标 / 示意数据）
## 4. 视觉分层（层级关系 / 强调轴 / 留白原则）
## 5. 交互关键帧（进入 / 切换 / 反馈）
## 6. Do / Don't
## 7. 未决项（传给 pm-notes）
```

## 每节写作指引

### §1 定位
- 一句话：这个模块在主界面的什么位置，承担什么职责
- 引用 master PRD L3 的硬约束（`见 master §L3`）
- ≤ 5 行

### §2 状态清单

所有可能的状态穷举成表格，这是 UI PRD 的**主承重**：

```
| # | 状态名 | 触发条件 | 视觉特征 | 文案要点 |
|---|---|---|---|---|
| 1 | 默认态 | 首次进入 | ... | ... |
| 2 | 有数据 | ... | ... | ... |
| 3 | 空态 | ... | ... | ... |
| 4 | 加载中 | ... | ... | ... |
| 5 | 错误态 | ... | ... | ... |
```

**审计检查**：每个 UI 模块至少考虑默认 / 有数据 / 空态 / 加载 / 错误五种；如果某种状态不适用必须显式标注"不适用，因为 <理由>"而不是省略。

### §3 内容清单

所有出现在 UI 里的文字 / 图标 / 示例数据都在这里列出：

```
**标题**：<成品文案>
**副标题**：<成品文案>
**按钮**：<文案>（主）/ <文案>（次）
**空态**：<成品文案>（至少 2 句：说明 + 引导）
**错误**：<文案> — 对应哪种错误
**示例数据**：<3-5 条示例，用于设计稿展示>
```

**禁止占位**：不允许写"<友好的提示文字>"，必须给出真实可用的句子。

### §4 视觉分层

不规定像素 / 字号 / 颜色（那是设计师决定），但要给出**分层关系**：

- 哪个元素是视觉主角？次角？陪衬？
- 强调轴是什么（大小？明度？运动？留白？）
- 如果多个元素竞争注意力，优先级怎么排
- 留白原则：哪里必须留白、哪里可以紧凑

### §5 交互关键帧

描述关键交互的**前中后**状态变化，用"时刻"而不是动效参数：

```
**进入模块**：
- t0：页面加载完成，模块区域显示 <某种状态>
- t1：数据到达后，切换到 <另一种状态>（切换感受：柔和/瞬时/?）

**用户点击主按钮**：
- t0：按钮按下，给出即时反馈（视觉或触感）
- t1：操作完成，展示结果 <形态>
- t2：若失败，回到原状态并显示错误提示
```

不写 CSS 动画参数、时长 ms 这些——交给设计师/前端判断。

### §6 Do / Don't

列出 3-8 对具体示例，每对都配"为什么"：

```
| Do | Don't | 为什么 |
|---|---|---|
| <具体画面描述> | <具体画面描述> | 引用 master L4 / L5 |
```

**检查**：每个 Do/Don't 都要能被截图或草图表达——无法图示化的说明还太抽象。

### §7 未决项

这一节记录"设计阶段暂时无法定案、留给 PM/产品后续决策"的事项。不要逃避——把不确定写出来比假装确定更有价值。

```
- [ ] <未决项描述> — 卡在哪里 / 需要什么信息来决策
```

此节内容会同步到 产品笔记.md 的对应章节。

## 完成判据

- [ ] 所有适用章节均有内容（不适用章节显式标注）
- [ ] §3 内容清单里没有占位符
- [ ] §6 的 Do/Don't 每对都可图示化
- [ ] 总行数 150-300
- [ ] 无数据字段、接口定义、算法细节
- [ ] 文件头锚点正确指向 master 和 shared

全部满足后：
1. 把文件头的 TODO 注释删除
2. 提醒用户可以调用 `prd-review` skill 审查
3. 交还给 prd-workflow agent
