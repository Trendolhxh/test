# prd-master

写需求的 **master PRD**。目标是让全员（产品 / 设计 / 开发 / 外部合作方）拿到这份文档就能对齐共识；后续任何模块 PRD 的撰写都会回来参照它。

## 何时触发

- `prd-workflow` agent 判定当前处于阶段 1
- 用户明确要"起草 XX 需求的 master PRD"
- 已有 master PRD 但需要重做

## 输入

`<feature-name>`：需求短名（例如 `homepage-redesign`、`sleep-coach`、`weekly-review`）。

## 输出

`prd/<feature-name>/主文档.md`，结构固定如下：

```
# <Feature 中文名> · Master PRD

> Status: Draft | Review | Locked
> Last updated: YYYY-MM-DD

## L1 · 问题定位（一句话）
## L2 · 核心指标 / 心智模型
## L3 · 主界面硬约束
## L4 · Do / Don't（抽象词审计）
## L5 · 消失测试
## L6 · 场景 Trigger 映射
## L7 · 砍项清单
## L8 · 模块切分方式（本次共识）
## 附录 · Q&A 推导（可选）
## 变更日志
```

## 核心行为铁律

1. **分批写入**：一次 Write/Edit 最多推进 1 个 L 层。写完停下来，简要问用户"L_ 共识如此，是否进入 L_+1？"
2. **不自作主张**：每一层都要先问用户，不要填好内容再让用户审。尤其 L1 问题定位、L2 指标、L4 Do/Don't，这些是"共识"不是"写作"。
3. **抽象词必配 Do/Don't**：L4 阶段如果用户说"让界面更 xx"这种抽象词，立刻追问具体的正反例，不允许抽象词进入文档没有对应 Do/Don't。
4. **不写推导过程到正文**：正文只留"共识结论"，推导过程存进"附录 · Q&A"里可折叠。
5. **Master PRD 目标简洁**：除附录外，正文控制在 300 行以内。L1-L7 每层通常 10-40 行。

## 七层收敛漏斗（逐层执行）

### L1 · 问题定位（一句话）

问用户：
- 这个 feature 解什么问题？给谁？在什么时刻？
- 有没有用户原话 / 真实场景可以引用？

目标：一句话 ≤ 40 字，能让陌生人立刻明白要解决的是什么。

写入形式：
```
**一句话**：<句子>
**用户原话**：> <引用>
**取舍链路**：<为什么是这条路，不是别的>
```

**卡壳信号**：如果用户给出的一句话能换成任何其他 feature 都成立（例如"让用户更爽"），直接退回，要求具体到"什么场景 / 什么动作"。

### L2 · 核心指标 / 心智模型

问用户：
- 用什么指标衡量这个 feature 成功？
- 对应的用户心智模型是什么（用户脑子里的那个概念）？

写入形式：
```
**核心指标**：<指标名 + 定义>
**心智模型**：<一句话描述用户怎么理解这件事>
**反例**：<不属于这个指标的情况，排除掉>
```

**卡壳信号**：指标无法被直接观测（"用户满意度"这种）→ 退回，要求可测量的代理指标。

### L3 · 主界面硬约束

问用户：
- 这个 feature 的主界面（首屏 / 主 tab / 主弹窗）是什么？
- 有哪些**不可动摇**的约束？（例如屏幕高度只能容纳 3 个卡片，或必须在 2 秒内完成）

写入形式：
```
**主界面**：<描述>
**硬约束**（按优先级）：
1. <约束>
2. <约束>
3. <约束>
```

**卡壳信号**：约束多于 5 条 → 退回，要求取舍到不超过 5 条。

### L4 · Do / Don't（抽象词审计）

问用户：L1-L3 里提到的所有抽象词，每个都要配一对 Do/Don't 示例。

审计流程：
1. 扫描 L1-L3 的正文，列出所有抽象词（"高能"、"轻"、"聚焦"、"自然"…）
2. 对每个抽象词问："具体什么样算 Do？什么样算 Don't？给我可看的例子。"
3. 如果用户答不上来 → 标红这个词，标注"待具体化"，不允许它在后续 PRD 出现

写入形式（表格）：
```
| 抽象词 | Do（具体） | Don't（具体） | 状态 |
|---|---|---|---|
| 高能时长 | 具体描述 | 具体描述 | ✅ 已具体化 |
| 聚焦 | — | — | ❌ 待具体化 |
```

### L5 · 消失测试

问用户：
- 如果这个 feature 做得好，用户**不会注意到**它的哪些部分？
- 哪些部分反过来**必须醒目**？

写入形式：
```
**应隐形**：<列表>
**应醒目**：<列表>
**判据**：用户打开界面后第一眼看到的是「<X>」，不是「<Y>」
```

### L6 · 场景 Trigger 映射

问用户：列出 3-5 个典型使用场景，每个场景：
- trigger（用户在什么情境下打开 / 触发）
- 期望看到的响应
- 不期望看到的响应

写入形式（表格）：
```
| 场景 | Trigger | 期望响应 | 不期望响应 |
|---|---|---|---|
```

### L7 · 砍项清单

问用户：原始设想里有哪些被**砍掉**了？理由是什么？

写入形式：
```
| 砍掉的项 | 理由 | 溯源到哪一层 |
|---|---|---|
```

**作用**：让未来的同事看到这份 PRD 时，知道"为什么不做 X"——避免同样的建议反复被提出。

### L8 · 模块切分方式（关键共识层）

这一层是 iSho 流程的**独特加项**，目的是让下一阶段（prd-decompose）有清晰依据，而不是凭感觉拆。

**步骤**：

1. 基于 L1-L7 的内容，主动给用户**至少 2 种候选切分维度**。常见维度：
   - **按 UI 区块切**（hero / timeline / input-area …）
   - **按能力闭环切**（ingestion / evaluation / presentation …）
   - **按数据流切**（数据源 / 状态机 / 视图层 …）
   - **按交互流程切**（进入 / 浏览 / 触发 / 反馈 …）
   - **混合**（顶层一种维度 + shared/ 承接跨模块契约）

2. 对每种候选，简要说明**在本需求下**的优劣势（不是通用优劣）。例如 homepage-redesign 里"按 UI 区块 + shared 契约层"优于"纯 UI 区块"，因为有 Events Schema 这类强跨模块数据。

3. 让用户选一个，或明确反馈要混合/自定义。

4. 写入 master PRD：
```
**本次切分维度**：<名称>
**理由**：<一句话，引用哪几条 L1-L7 的结论>
**预期模块清单**：<模块 A / 模块 B / 模块 C>（初稿，prd-decompose 会细化）
**共享契约候选**：<契约 A / 契约 B>（若无可为空）
```

**卡壳信号**：用户无法在 2-3 个候选中做选择 → 说明 L1-L7 还不够清晰，回退前面的层补充，不要硬推 L8。

## 交互要点

- 每一层开始时，简短告诉用户"现在我们进入 L_，聊<XX>"，不要直接甩结构问题
- 用户的回答可能零散 → 你负责归纳成结构化结论，回读给用户确认后再写入
- 写入后简要预览（展示刚写的片段），再问是否进入下一层
- 不要把"L1-L8 全走完"当作必达目标——有层发现前置没想清楚就退回

## 完成判据

主文档.md 满足以下全部：
- [ ] L1-L7 每层有内容
- [ ] L4 的抽象词审计表里没有❌ 待具体化
- [ ] L8 有明确的"本次切分维度"声明
- [ ] 正文（不含附录）≤ 300 行
- [ ] 用户明确说"可以进入 prd-decompose 了"

满足后：
- 把 主文档.md 头部 `Status` 改成 `Review`
- 交还给 prd-workflow agent
- **agent 收尾动作**：创建 `prd/<feature>/进度.md`（用 prd-workflow 附录「进度.md 模板」），初始化四阶段 checkbox / 模块矩阵占位 / 变更日志首行
